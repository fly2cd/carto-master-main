## 一、结论与使用方式

本方案依据 [制图智能体总体流程](制图智能体总体流程.md) 的 A0–A5，细化主要改动位置、改动内容、工作量、风险和验收次序。三类任务说明分别提供专业要求：[标准专题图](标准专题图制图流程说明.md)、[海报地图](海报地图流程说明.md)、[领导调研用图](领导调研用图制图流程说明.md)。

**总体判断**：不需要推倒重写，但也不是增加几个 CLI 命令的小修。应保留现有状态、候选编译、渲染证据、模板仓库和交付事务机制，先纠正文档与实际安全能力的差距，再在同一条实现链中增加设计修订、审图和多类型数据处理。

**原始基线发现与后续复核**：本计划初次静态复核发现，审批代码当时缺少目标要求的 nonce 和完整声明校验。2026-11-12 后续读取已见 `NonceStore`、`revise`、成品 `review`、`BudgetStore` 等新增内容，详见 [Phase 2 设计与实现说明](Phase2设计与实现说明.md)第十四节。这说明代码已有推进，不代表 A1.1/A1.2/A1.3 已通过验收；必须继续检查授权对象、原始版本、预算和恢复等实际行为。下文基线数据与 D01–D13 保留为初始差距记录，不能直接用来断言最新代码仍完全相同，也不能只因新增入口就把问题标为已关闭。

**Phase 2 专题设计的使用位置**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)应在 **A0** 纳入合同与状态评审，作为 **A1.2 和 A1.3** 的主要实现参考，再由 **A2–A4** 填充数据、业务与构图能力，A5 按其测试清单验收。它细化既有工作包，不增加新的实施阶段，也不表示应等到实施 A2 才开始设计。

建议分三档看投入：

| 交付档位 | 范围 | 基础工程工作量 | 含 25% 预留 |
|---|---|---|---|
| M1：先修稳当前核心 | A0 + A1，仅使用已准入栅格场景验证安全、修订、审图和恢复 | 32–50 人日 | 约 40–63 人日 |
| M2：三类业务受限试点 | A0–A3，具备有限输入、有限布局下的三类任务闭环；尚未完成 A5 总体验收 | 92–152 人日，累计 | 115–190 人日，累计 |
| M3：本方案约定范围的完整目标 | A0–A5，包括受控构图/媒介扩展及三类真实任务和运行验收 | 132–220 人日，累计 | 165–275 人日，累计 |

人日是工程投入，不是自然日。范围、估算前提和未包含能力见第七节；建议先批准 M1，验收后再确认后续投入，不一次承诺所有扩展。

### 4.2 W01：先明确真正的批准对象

建议 A0 先建立一张“签发对象—验证入口—受影响产物”表，再改代码。

- G1：批准特定简报和执行范围，不能只验证某个字符串动作。
- G2：继续绑定候选、执行、预览和环境，并按新协议加入要求的审图依据；不是只批准裸候选或一张图片。
- G3：批准完整 Manifest，包括精确成品、接收方、目的地及必要审查依据。
- T1：批准模板简报。
- TP：当前代码实际计算的是 `{package_digest, evidence_digest, repository_scope}` 的发布对象摘要。建议保留“包 + 验证证据 + 发布范围”的含义；机器 object_type 的名称由 A0 统一，不能误改成只批准包摘要。

完整票据和受信执行上下文应覆盖仓库要求的身份、动作、对象摘要、作用域、环境、策略、时间和唯一标识。单用户部署可以使用简单身份体系，但不能把模型传入的 subject_id 当作身份认证，也不能因“单用户”就省略防重放。

nonce 的消费与执行必须有持久记录：先留下准确的执行意图，再保证只消费一次；崩溃恢复只能恢复同一对象、同一事务，不能借恢复接受另一运行的重放。签名密钥不能进入模型上下文。

### 4.3 W02/W03：原请求不改，设计以新版本进入

保留 `JOB_INPUT_DRIFT`。目标不是让原请求可随意修改，而是增加明确的设计修订操作：

```text
不可变任务与已验证授权
    ↓
新的设计提案 → 范围与能力检查 → 新 MapPlan 修订
    ↓
新候选 → 新预览 → 新审图记录
    ↓
选定具体版本 → G2 → 新锁
```

首版只允许现有能力中的少量设计变化，例如在数据和面板数不变、类别定义兼容的条件下切换已准入图例模式。不要在 A1 同时开放任意画布、自由布局、新表达和数据源替换。

需要共同改动：

1. 明确授权版本、设计修订、候选、预览尝试、正式渲染 attempt 和交付事务的不同身份。
2. 为各版计划、候选、预览使用不覆盖历史的路径；选定版本由受单写锁/CAS 保护的状态引用，不靠文件名“最新”或目录排序判断。
3. 修改 freeze、`_locked_render_inputs`、render、check、deliver 的加载与重验，不能只在 compile 换目录。
4. 每次提案先比较实际批准范围。范围无法证明仍被覆盖时，首版要求新 G1，而不是猜测允许。
5. G1 回执不重复消费；后续动作根据已经验证、持久保存且仍有效的运行授权执行。授权持续多久、何时需要重新签发须由协议和政策明确，不能暗自忽略时效。
6. 预算在运行级持久记录。多次 CLI 调用、进程重启和 retry 不能重置总预算；预留费用、实际消耗和故障重试如何计数要有明确规则。
7. 宿主可提交语义参数提案，但不可提交任意 Python、SQL、GIS 表达式或完全由模型拼装的可信执行对象。

不必为每项职责新增 CLI。若增加 `revise`、`review` 或受控重渲染操作，只能放在唯一 `carto` CLI 的适当子命令中；这些名字是设计候选，不是当前已存在的命令。

### 4.4 W04：审图结果进入批准对象，不能冻结后补写

设计审图记录至少应关联候选、预览、审阅身份、结论、问题和接受范围；成品审查应关联实际输出、检查报告、输出目标和所需时效/媒介条件。

目标顺序：

```text
设计：候选与预览 → 审图依据齐备 → G2 → 锁
成品：按锁输出 → 自动终检 → 约定审查 → 冻结 Manifest → G3 → 交付
```

当前 `check` 中“检查”和“生成 Manifest”应在内部职责上分开。是否新增步骤，由状态转移表决定，不为了名称整齐机械增加命令。

审图结果不是一个可自行填写的 `passed: true`。自动检查、模型建议、业务采用和人工批准要明确区分；数据不变并不意味着另一版布局可以沿用旧 G2。

### 4.5 W05/W06：准备服务交付真实结果，不只交付结构

优先扩展已有 `source-manifest`、数据包和 artifact 引用，而不是再建一套材料目录。

- 原始文件保持不变；解析结果、人工纠正、业务采用和设计派生文件分别引用其上游。
- 文档保留段落/表格/对象定位，图片或扫描件保留页和区域；源文件改变后旧定位不能继续使用。
- OCR 的置信度不是事实真实性。影响关键数字、单位、时间或地点的歧义必须核验或保留未决状态。
- 数据统计、业务解释和颜色/图例定义分别管理；配色变化不重读全部数据，数据变化必须使依赖文案、图表与预览失效。
- 网关上下文应来自已经验证的授权或明确的获准辅助入口；`ExecutionContext.from_generate_request()` 只是构造上下文，不是鉴权。
- 宏、脚本、嵌入指令、外部引用和模型输出均不能自动执行。新增依赖和外部服务需显式选择与批准，不自动安装。

### 4.6 W07–W11：按业务最小链逐步扩展

- **专题**：先利用已有栅格链和矢量工程候选，验证明确的输入和表达；不同时承诺全部统计方法、任意数据格式和任意投影。
- **海报**：先在有限区域布局中支持地图、短文本、图片和一种基础图表，并检查它们的数据关系；自由叠置和复杂版式放 A4。
- **调研**：先做单日、固定停靠顺序、单一交通方式的示意/道路参考；接入一种定位服务和一种道路服务，逐项保留请求、结果、入口及采用证据。不把求路失败自动当作直线产品成功。
- **项目内设计**：将已验证的完整设计合同交给统一编译链，不只是允许 template 为空。依赖、资源、输出和检查规则仍须闭合。
- **自由布局/输出**：先受控区域和必要的明确叠置，后续再扩大；固定输出配置及检查条件。算法优化需先符合设计原则，不以求解器代替设计授权。

## 五、协议、状态和发布切换设计

### 5.1 优先演进的现有合同

| 合同组 | 主要变化 | 必须联动的消费者 |
|---|---|---|
| approval-receipt / 安全策略 | 完整声明、唯一性与恢复语义 | 全部五个 gate、签发/验证入口、仓库与恢复 |
| map-brief / generate-request | 不可变任务、授权范围、允许设计项 | intake、brief、提案检查、准备器和场景准入 |
| job-state / step-receipt / map-plan | 设计修订和选定候选引用，与状态 revision/attempt 区分 | 编排、状态、恢复、候选及锁加载 |
| source-manifest / prepared-data-bundle / raster-prepared-data / resolved-portrayal | 来源、提取、采用与表达分离 | 数据服务、计划、图例、渲染和终检 |
| resolved-map / map-preview-evidence / map-spec-lock | 明确版本及所需审图引用 | compile、preview、freeze、render、check、deliver |
| page-request / page-bindings / page-output / resolved-layout | 类型化内容、布局和整版关系 | 组件编译器、页面渲染器、回执和检查器 |
| validation-report / delivery-manifest | 专业审查与成品对象形成顺序 | check、G3、交付和恢复 |

确有独立责任时才新增少量“提取记录、采用记录、设计提案、审图记录”等合同；A0 决定名称和归属。不能为了避免版本升级把不同语义全部塞进不受约束的扩展字典。

### 5.2 先写状态转移表，再写命令

最小转移应覆盖：新任务、获准准备、提交设计修订、编译、预览、待审阅、待 G2、已冻结、正式渲染、终检/成品审查、待 G3、已交付，以及各类失败。

尽量复用现有状态含义，仅新增确有必要的 step 或状态。对每个转移明确：前置对象、权限、会读取/写入的产物、是否消费 nonce、预算变化、失败后状态和可恢复证明。

必须区分：

- **设计失败**：回到拥有该决定的设计或业务层，形成新修订。
- **可恢复执行故障**：在原锁、固定输入和已验证环境下新建 attempt。
- **证据漂移、越权、未知能力**：拒绝，不进入普通自动重试。
- **提交结果未知**：查询事务与最终包，不能重复消费批准。

### 5.3 不做并行旧格式兼容

- 新协议和当前消费者一次协调切换，不新增旧字段别名、旧锁解释器或请求 wrapper。
- 升级前清点未完成运行。已完成成果保留；不能安全续跑的旧运行保存证据后用新协议重新准备和批准，不改旧锁。
- 回退只回到满足当前安全底线、且与其数据格式一致的已验收版本；不能为回退而重新开放缺少防重放的票据或降低质量门。
- 新格式对象不交给旧代码猜测读取。安全条件不满足时应暂停相关能力，而不是为“可用”继续旧的不合规链。
- 分阶段启用新能力，不等于放宽安全开关。功能开关只能控制已验证能力是否开放，不能跳过审批或检查。

## 六、主要风险与控制措施

风险等级表示影响和不确定性，不是声称已测得发生概率。

| 风险 | 等级 | 容易出问题的地方 | 控制与停止条件 |
|---|---|---|---|
| R01 审批基线与要求不一致 | 极高 | 票据有签名却缺身份/范围/唯一性验证 | A1.1 先补齐；五个 gate 的正反例和恢复未通过，不扩大业务能力 |
| R02 nonce 消费与崩溃恢复冲突 | 极高 | 正常恢复被拒，或借恢复重复执行 | 持久意图、唯一消费、事务重验与故障注入；无证明则拒绝恢复 |
| R03 旧预览批准新设计 | 极高 | 固定路径、run_id 级证据 ID、选定版本漂移 | 全部版本独立引用；签发、冻结、重放均核验精确候选与预览 |
| R04 请求修订绕过原授权 | 极高 | 删除 JOB_INPUT_DRIFT，或把范围扩大解释为版式变化 | 原任务不变；提案白名单和批准范围比较；无法证明覆盖就重新 G1 |
| R05 跨命令预算重置 | 高 | 新上下文把计数清零，重启继续无限循环 | 运行级账本、原子预留/结算、重试计数规则和预算负例 |
| R06 数据/表达拆分后的漏更新 | 高 | 数据已变，数字、文案或图例仍引用旧结果 | 依赖关系与版本失效测试，完整候选审查；不只比图片外观 |
| R07 OCR/提取或素材外传 | 高 | 识别值被当原始事实；文档指令或未授权服务外传 | 来源位置、纠正/采用记录、格式/大小边界、默认拒绝外部动作 |
| R08 复合页面“各组件对、整版错” | 高 | 图例、单位、颜色、文字和地图不一致 | 组件与整版双层检查；统一事实引用及明确比较关系 |
| R09 出行图被误作可用导航 | 高 | 错入口、陈旧路网、时间冲突、直线冒充道路 | 用途分级、入口/路线/时效验收；导航独立边界；关键条件未满足则停止 |
| R10 模板/能力边界变成任意代码入口 | 高 | 为无模板或自由布局允许脚本、动态模块或隐式 fallback | 声明式合同、受信组件、完整能力匹配和默认拒绝 |
| R11 字体、颜色、页面或依赖变化 | 中高 | 同输入不同环境输出变化；工程文件被称作印刷合格 | 固定依赖/字体/输出配置，实测成品；容差预先声明，不能失败后补放宽 |
| R12 Schema 版本和当前分支漂移 | 高 | 按旧文档字段开发、并发改核心合同 | A0 形成机器协议清单；每批改动有单一合同负责人和集成窗口 |
| R13 发布、格式切换与回退 | 高 | 新锁给旧版本读取，旧票据继续执行 | 提前清点运行、旧成果只读、新运行重新授权；不安全版本不作为回退目标 |
| R14 实际材料/专家/服务不可得 | 中高 | 代码完成但无法验证用途和精度 | 试点材料与确认人尽早确定；缺真实验收条件不宣布生产完成 |

不把“开发难度大”与“可以先放宽门禁”画等号。风险控制应形成代码、测试和发布条件，而不是只写在 README 中。

## 七、改动量与工程投入估算

### 7.1 估算包含什么

本估算包含技术设计、实现、自动测试、联调、技术文档和阶段内修复。业务专家审阅的外部工时、等待用户确认、取得真实数据/许可、采购服务及环境审批等待不计入人日。

约定范围：

- 保持单主智能体与模块化单体，不建设多租户 SaaS、调度平台或新的模型服务。
- 身份与审批满足仓库基线，但不扩张为完整组织管理系统。
- 文档支持有限 DOCX、可解析 PDF、常规表格、常用图片；OCR 只接一种获准引擎/服务，不训练模型，不承诺任意复杂扫描表格自动恢复。
- 不从参考图盲目恢复统计值或地理坐标；原图作为素材与事实重建是不同能力。
- 海报先有限布局、文本/图片及一种基础图表，再逐步受控扩展；不承诺任意自由排版都自动找到满意解。
- 调研先单日、固定顺序、单一交通方式，一种定位服务与一种路线服务，并完成一种明确坐标约定和显示 CRS 下的受信处理；不包括自动行程优化、实时导航、多城市离线路网维护或复杂车辆调度。
- A4 包含有限的项目内设计、区域布局/必要 inset 或受控叠置、一种明确印刷/输出配置。不默认纳入另一工作区的全部图片底图配准、原生像素模式和多路由容灾。
- 新的高级专题方法、复杂图册/多受众批次分发、任意文件格式或额外供应商，需单独评估，不由 25% 预留吸收。

### 7.2 文件与代码改动量级

### 7.4 如何理解日历工期

- 一名工程师全职、按每周 5 个有效人日，M3 大致是 **33–55 周**量级。
- 两名工程师加测试支持，如果团队每周实际完成约 7–8 个有效人日，大致是 **21–40 周**量级；不能直接除以人数，因为核心协议和验收存在串行依赖。
- 只先完成 M1，单人约 **8–13 周**量级；人员熟悉度、现有测试结果和身份来源方案会显著影响它。
- 以上不含外部等待，不给具体承诺日期。A0 后重估 A1；每阶段用实际完成记录更新后续区间，而不是反复改总体目标。

估算可信度：核心状态/审批改动为中等，OCR、调研服务、自由构图和印刷适配为中低；这些部分应先做小范围技术验证，再冻结下一批范围。

## 八、稳定的阶段实施计划

### A0：确认基线与关键合同，不先堆功能

**设计参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第三至六、八节。先确认输入输出、不可变版本、逻辑状态、授权持续、预算与操作幂等，再开展修订实现。

**进入条件**：维护者确认本次调整范围和应纳入基线的工作区变更。

**执行**：

1. 记录完整文件/协议版本清单与已知差异，确认安全基线和实际批准对象，优先解决 D01/D02/D13 的设计决策。
2. 确认真实 Python 3.11+ 和依赖；按仓库入口先做 CLI 帮助、Schema 自检，再在获得许可的环境运行基线测试。不得使用 WindowsApps 占位解释器或自动安装依赖。
3. 将测试失败、跳过、环境缺失和能力未开放分别记录；建立一条用户授权的受限栅格验收样本。
4. 固定状态转移表、身份来源、nonce 消费/恢复、授权持续时间和版本切换策略。
5. 为文档与代码中不一致的“已实现安全能力”建立修订清单，不能继续复制错误声明。

**交付**：基线记录、风险清单、合同与转移决策、验收样例清单、A1 精化估算。

**退出条件**：维护者确认安全要求、批准对象、测试口径和切换策略；未解决的身份或恢复语义不得带入功能开发。

### A1：先在现有栅格链完成可信的最小循环

#### A1.1 审批与防重放基线

**衔接参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第三、八、十三节。它定义循环依赖的授权条件，不代替本阶段的安全与恢复验收。

- 先改 W01，并同步所有五个 gate、票据 Schema、签发/验证入口和事务调用者。
- 验证未知字段处理、对象类型、主体/范围、过期、篡改、跨运行重放和真实 nonce 唯一消费。
- 在消费前后、产物写入前后、状态提交前后注入中断；证明相同事务可以安全恢复，不同对象不能借恢复继续。
- 不增加新业务场景，不开放新文件类型或设计自由。

**可发布条件**：安全正反例与恢复全部通过；若不能满足，只暂停相关能力，不回退到低于安全底线的旧模型。

#### A1.2 设计修订、提案与持久预算

**主要实现参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第五至十节；按第十二节的最小例子接通提案、版本、编译、预览和问题路由，并落实第十三节相关反例。新增 revise 或预算文件不等于完成这些行为。

- 分离不可变任务与设计修订，版本化计划/候选/预览路径，更新全部读取者。
- 将受限提案接口接入正式主链；保持编译器唯一生成执行对象，不让模型直接制作受信 RenderScene。
- 实现运行级累计预算，跨 CLI 与重启保持一致。
- 用现有数据、相同面板数下的一项已准入参数变更证明“预览→合法修订→再编译”。

**可发布条件**：至少连续两次设计修订仍能正确追溯；修改原请求、越权提案、过期授权、旧预览混用和预算重置均被拒绝。

#### A1.3 审图、清单时机与合法恢复出口

**主要集成参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第七、八、十一、十三节。区分迭代评价、Phase 3 设计审图和 Phase 4 成品审查，绑定选定候选及准确批准对象；不能把成品 review 入口当作 Phase 2 已有设计审阅。

- 把设计审图与成品审查关联到具体版本；按约定顺序形成 G2/G3 对象。
- 拆分自动终检与 Manifest 形成职责，补齐失败分类与显式修订/受限重渲染出口。
- 验证 G3 前绝不交付、G3 后提交不确定时可查状态，恢复不重复消费批准。

**A1 整体验收**：同一受限栅格任务完成“真实 G1→预览→两次合法修订→审图→G2→锁驱动输出→终检/成品审查→G3→交付”，历史产物不覆盖，全部安全反例通过。这是 M1，不等待 OCR 或新场景。

### A2：统一数据与素材处理

**接口参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第四、七、十、十二节。补齐处理、采用、来源与失效接口，不另做一套设计循环。

**前置**：A1 的版本、授权与证据机制已验收，A0 的数据采用责任已确认。

1. 先拆数据事实、语义和表达，保持现有栅格结果与检查不退化。
2. 接入普通文档、表格和图片提取，保留来源定位；先解决可明确解析的材料，再接 OCR。
3. 接一种获准 OCR 方案，定义不确定性、纠正、采用与禁止外传规则。
4. 让准备服务产生实际结果和工具证据，不把空回执或预填 passed 当数据验收。

**验收**：换配色不重算未变化统计；修改原文关键数字使依赖的图表/文案/候选失效；OCR 误识别可追溯纠正；恶意材料指令、未知格式、超限文件、未授权外传明确拒绝。

### A3：业务最小闭环逐项接入

**业务接入参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第四、七、十二、十三节。三类业务通过受信组件和问题分类接入同一协调器。

A3 不一次开放全部业务开关，三个子包分别验证、登记和交付。

| 子阶段 | 先做的范围 | 主要验收 |
|---|---|---|
| A3.1 专题 | 重构与总体流程冲突的旧入口；显式 design 驱动，复用数据、修订与交付链 | 数值进入表达与渲染；旧审批不批准新版本；单位、类别、图例、比例正确 |
| A3.2 海报 | 有限区域布局中的地图、短文本、图片和一种基础图表 | 图文同源、单位时点一致、没有占位/缺字/溢出；整版而非单组件通过 |
| A3.3 调研 | 单日固定顺序，明确地点/入口，一种定位与一种道路服务 | 行程忠实、入口确认、坐标与显示 CRS 处理有据可核、路线模式/时间/来源正确；道路失败不冒充示意成功，隐私检查通过 |

#### A3.1 的四个实施步骤

| 步骤 | 主要内容 | 验收重点 |
|---|---|---|
| A3.1-a 接口与责任 | 显式 geometry / map_title / design；模板按能力适配，成品审查不挪用 G2 | 旧请求/歧义几何拒绝；G1 批准简报，G2 冻结候选，G3 批准交付对象 |
| A3.1-b 数据与语义 | A2 CSV 提取接属性连接；明确字段、单位、度量、归一化；冻结素材依据 | 数值实际进入准备结果；重复/漏连/非有限值/无授权连接拒绝 |
| A3.1-c 有限专题表达 | 类别、等距/手工分级设色、总量面积比例符号；生成 MapPlan v4 | 改指标/数值改变执行结果；图例与符号、断点、单位一致 |
| A3.1-d 共享链路验收 | 真预览/锁驱动输出/终检/成品审查/G3；不可变修订与恢复 | 旧文件不覆盖，旧 G2 不批准新预览；恢复不重复计修订预算；图片像素响应数据变化 |

A3.1 **不以兼容旧请求、旧模板驱动或旧调用顺序为条件**。保留合理的受限栅格能力与确定性执行，不保留冲突设计。自由布局、无模板项目设计、连续栅格表达、OCR、自动设计迭代策略仍受 A2 后续/A4 范围约束。

实现与测试记录见 [A3.1 专题核心实施记录](dev-log/A3.1-thematic-core.md)。合成工程验收不等于下面要求的真实授权业务验收，不得用测试签名替代，也不据此开放生产任务。

每个子阶段都要用对应真实授权材料做一次完整任务验证，不能把真实任务全部推迟到 A5。A5 负责三类共同运行及最终发布验收，不替代各能力自己的验收。

不在 A3 引入任意自由布局、任意算法和实时导航；M2 是三类任务的受限工程试点，不是全范围生产承诺。

### A4：构图、项目内设计与媒介扩展

**能力扩展参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第七、十至十三节。新增组件和布局必须保持版本、预览、审阅和失效规则，不扩大循环本身的权限。

**前置**：A3 中相关内容类型和检查合同已经可用；需要调整设计原则的议题已正式确认。

建议拆成三批，不一口气改全部渲染体系：

1. **项目内设计与合同解析**：相同验证链接受完整、受信的项目设计；不通过空模板或脚本绕过原检查。
2. **受控区域布局与必要叠置**：先明确父子、层级、保护区和不可移动地理锚点，再实现解析或已批准求解器；输出无解诊断，不静默删内容。
3. **一种明确输出/印刷配置**：固定字体、颜色/输出意图、页面、图像有效分辨率与检查规则，按真实用途验收。

**验收**：无匹配能力时失败关闭；修改组件使整版证据正确失效；屏幕与印刷版符合各自冻结配置；不存在临时换字体、换素材、换路线或失败后放宽容差。

### A5：三类任务与运行发布验收

**验收参考**：[Phase 2 设计与实现说明](Phase2设计与实现说明.md)第十三节，并结合三类真实任务补足业务、媒介与交付检查。

1. 执行三类代表任务，覆盖合法路线、复杂材料、必要修订、真实批准、实际成品与交付。
2. 复测全部 gate、角色与范围、文件路径、未知字段、秘密外泄和材料指令风险。
3. 演练提案/预览/冻结/渲染/检查/交付各节点中断，重复请求、并发写、预算用尽和升级/回退。
4. 对调研做必要时效与用途核验；对海报按约定做媒介/打样验收；对专题核对比较与表达。
5. 同步真实 CLI、工作流、Schema、策略、Skill 和审批说明；决定哪些能力可正式登记，哪些仍是工程预览。

**退出条件**：每项必需成果及全部阻断性检查通过，已知限制透明、恢复可验证、交付准确。生产准入仍由相应责任方决定，不能自动设置 `production_enabled: true`。

## 九、让计划稳定执行的工程规则

### 9.1 每批改动要小，但必须完成对应责任

- 一批只处理一个明确协议变化或可验收行为；对应生产者、消费者、正反例和说明一起修改。
- 不把“先改 Schema、后面再补所有消费者”作为可发布中间状态。
- 不把纯文件搬迁和大幅行为变更混在同一批中，避免难以定位回归；需要拆模块时先证明行为不变。
- 审批、状态、锁和交付的核心合同指定一个技术负责人，防止不同场景同时改出不同解释。
- 可并行的是已固定接口后的独立解析器或领域实现，不是同时修改同一状态机和共享票据。

### 9.2 每阶段固定六项验收材料

1. 范围与不做事项；
2. 改动文件和协议版本；
3. 合法、非法与故障恢复用例；
4. 实际测试结果，包括跳过与原因；
5. 一次代表任务的产物与审阅记录；
6. 发布、旧运行处置和回退说明。

没有实际结果的测试项不能填写“通过”。测试中的合成批准、模拟服务和合成数据必须隔离标识，不能成为正式业务证据。

### 9.3 阶段停止条件

出现下列情况，应停止下一阶段投入，先解决当前问题：

- 签发身份、防重放、对象或时效仍说不清；
- 新设计仍需覆盖旧请求或旧候选才能继续；
- 出现无法解释的输出或依赖漂移；
- 终检失败只能靠改状态、删证据或降级检查来恢复；
- 新材料类型能进入主链，但没有提取来源与业务采用；
- 必要服务、真实数据或审阅责任方无法提供，导致用途无法验收；
- 为赶进度需要开放未知字段、任意脚本、旧格式兼容或不安全回退。

停止不等于丢弃已完成工作：保留已验收版本与证据，重新确认范围或技术方案。稳定计划依赖明确的退出条件，不依赖假定所有阶段一次成功。

## 十、第一批建议实际做什么

在真正开始改代码前，建议先完成以下清单，不立即修改三类场景：

- [ ] 维护者确认当前工作区哪些修改组成基线，记录全量版本和已知问题。
- [ ] 确认当前简化审批与仓库目标的差距；决定符合要求的身份来源和防重放方案。
- [ ] 明确 TP 的实际发布对象，以及所有 gate 的声明与摘要来源。
- [ ] 在明确许可和真实解释器下执行 Schema、基础安全、状态与现有栅格链测试，记录真实结果。
- [ ] 定义最小设计修订例子、允许变化字段、G1 覆盖与预算规则。
- [ ] 定义审图记录与 G2、成品审查与 Manifest/G3 的形成顺序。
- [ ] 写出 nonce 消费、候选选择、终检失败和交付提交中断的恢复测试。
- [ ] 冻结 M1 的范围和修订后的估算，再进入 A1.1。

上述是后续执行清单，不表示本次已经完成。**最优先的改动不是新增海报或调研命令，而是让“谁批准了什么、哪一版设计正在执行、失败后怎样安全继续”在代码中成立。**
