可以。这条路线的核心是：**把“位置从哪里来、内容是否装得下、装不下怎么办”逐步工程化，而不是一次性建设一个通用自动排版系统。**

建议拆成四个阶段，每一阶段都能独立形成可用能力。下面是改动方案，不代表已经实施；提到的验收情形也只是后续标准，本次没有执行测试。

## 一、先明确目标：不重写现有闭环，补强冻结前的布局能力

当前主流程可以继续保留：

```text
intake → brief → compile → preview → freeze → render → check → deliver
```

要逐步完善的是其中的：

```text
compile → preview → freeze
```

最终形成：

```text
已批准的内容与表达要求
        ↓
解析布局契约
        ↓
测量真实内容
        ↓
形成一个或少量布局候选
        ↓
真实预览与独立检查
        ↓
在授权范围内修订
        ↓
G2 批准精确候选
        ↓
冻结并正式渲染
```

**正式 Renderer 仍然不负责重新设计。** 标题换行、图例换列、地图框调整等影响图面的决定，应在冻结前确定；冻结后发现设计问题，应回到修订流程，而不是让 Renderer 临时改变布局。

四阶段的区别可以概括为：

| 阶段 | 要解决的问题 | 完成后能回答什么 |
|---|---|---|
| ① 契约消费 | 坐标到底来自哪里 | “这个位置由哪个模板、哪个 Frame 决定” |
| ② 内容测量 | 给定位置是否装得下 | “这段文字、这些图例在这个框里需要多少空间” |
| ③ 候选与回调 | 装不下时怎么办 | “尝试了哪些允许的调整，为什么选择这一版” |
| ④ 模块关系与求解 | 多模块如何共同确定位置 | “这些模块为何这样分组、分区和分配面积” |

---

## 二、阶段一：让布局契约真正决定最终位置

### 目标

先不追求“聪明”，而是做到：

> **模板声明的布局，就是编译器使用的布局，也是渲染器执行、检查器验证的布局。**

现在模板里有毫米制 Frame，场景编译器又写了一套像素位置。这一阶段先消除两套位置来源。具体问题可对照 [模板布局定义](skills/carto-agent/scripts/carto_core/scenarios/synthetic_flood/author.py#L129) 和 [实际场景位置](skills/carto-agent/scripts/carto_core/scenarios/synthetic_flood/candidate.py#L139)。

### 1. 先确定一个明确的视觉基线

这里有一个不能跳过的选择：

- **以当前模板的 Frame 为准**：最终画面可能与当前固定坐标画面有所变化；
- **以当前成图效果为准**：把希望保留的位置整理成完整的新模板版本。

不能一边宣称执行模板，一边在代码中偷偷保留另一套位置。

若修改已发布模板的布局内容，应形成新版本并经过既有验证与发布流程，不能原地修改不可变包。

### 2. 补齐所有必要元素的容器和绑定

当前模板主要声明了主地图、图例、标题，但实际输出还包含：

- 指北针；
- 比例尺；
- 来源；
- 合成数据声明。

这些元素也需要有明确的位置来源，可以是：

- 独立 Frame；
- 或所属容器内的具名位置。

同时建立内容绑定，例如：

```text
标题内容       → title-frame
实际分类图例   → legend-frame
主地图视图     → main-map-frame
来源说明       → source-frame
强制声明       → notice-frame
```

**第一阶段不需要复杂的模块系统，但不能再存在“没有契约归属、由代码临时摆放”的必需元素。**

### 3. 建立统一的布局解析

建议在现有 `compiler/` 内增加布局解析能力，输入为：

```text
布局契约 + 输出规格 + 内容角色绑定
```

输出为确定的布局结果，例如：

```text
Frame ID
页面边界
内容区边界
单位转换结果
元素锚点与对齐方式
来源模板与摘要
```

这只是对现有候选执行信息的类型化补充，**不是再建一份独立的业务计划或第二份锁**。

单位需要明确区分：

- 物理尺寸，例如 mm；
- 页面逻辑坐标；
- 最终输出像素；
- 浏览器设备像素比例。

初期建议保持当前 A3 横向、144 DPI 的能力边界，先把这一种输出规格做一致，再扩展其他尺寸。不能把一个 mm→px 公式不加区分地用于所有浏览器与 PDF 环节。

### 4. 真正渲染到地图框，而不只是调整相机 padding

这是阶段一中较重要的技术改动。

页面大小与地图内部视口应分开：

```text
页面画布
└─ 地图 Frame
   └─ 地图内部视口、相机和地理内容
```

地图依据自己的 Frame 尺寸适配地理范围，再合成到页面对应位置。

不能仅用整页地图加 padding 来代替地图容器，也不能为了填满框而随意裁掉必保地理范围。

标题等元素则依据自己的 Frame、对齐方式和锚点生成坐标。

### 5. 让模板验证、地图生成和检查共用这套解析结果

至少贯通三处：

1. 模板验证使用它生成验证场景；
2. 地图生成使用它生成真实候选；
3. 版面检查使用它判断边界和绑定。

否则只是把坐标从一个文件搬到另一个文件，没有解决一致性问题。

### 阶段一的验收标准

可以用以下变化检验：

- 修改图例 Frame 的位置，最终图例随之移动；
- 修改标题 Frame 的宽度，候选中的内容区宽度随之变化；
- 移动主地图 Frame，地图视口和页面合成位置同步变化；
- 缺少强制声明绑定，明确失败；
- Frame 越界或出现不允许的重叠，明确失败；
- 新布局产生新摘要，旧预览证据不能继续使用。

**这一阶段允许只支持固定 Frame。** 对尚未实现的 `shrink`、分页等策略，应明确拒绝或限制，不能只保留字段而声称已经执行。

## 三、阶段二：让真实内容决定“这个框是否够用”

### 目标

阶段一解决“框在哪里”，阶段二解决：

> **这个版本的内容，使用这个字体和样式，放进这个框后是否完整、可读。**

当前检查主要按字符数估算文字宽度，不能替代真实排版测量。参见 [现有边界估算](skills/carto-agent/scripts/carto_core/workflow/map_final_check.py#L443)。

### 1. 先只测量当前已有的内容

建议从四种对象开始：

- 标题；
- 图例；
- 来源；
- 强制声明。

暂时不引入企业名单、统计图和复杂地图注记，以免把工作范围扩大到复合专题页。

### 2. 补齐可执行的文本与图例样式

准确测量的前提是“实际绘制规则已经明确”，包括：

- 字体文件及摘要；
- 字号、字重；
- 行高；
- 换行规则；
- 内边距；
- 图例符号尺寸；
- 符号与文字间距；
- 图例行距、列距。

这一步不要求立即开放完整的独立 MapStyle 创建业务，但必须让测量和绘制消费同一份已解析样式，不能一边按默认字体测量，另一边按实际字体输出。

### 3. 建立测量接口和测量结果

接口可以在概念上表达为：

```text
measure(
  内容版本,
  内容区宽度,
  已解析样式,
  允许的排布方式,
  渲染环境
)
→ 测量结果
```

返回内容至少包括：

| 信息 | 用途 |
|---|---|
| 实际宽高 | 判断容量 |
| 实际行数 | 解释换行与高度变化 |
| 是否溢出、溢出方向 | 指导修复 |
| 实际内容边界 | 边界与重叠检查 |
| 字体、内容和测量器摘要 | 防止复用过期测量 |
| 测量适用条件 | 明确结果对应哪个宽度与样式 |

例如：

```text
标题完整显示需要两行
所需高度超过当前内容区
未发生内容截断
建议扩大标题区或采用已允许的双行布局
```

比“标题字符数超过上限”更有操作价值。

### 4. 测量与最终绘制保持一致

应尽量使用相同字体和相同排版实现完成测量与绘制。

可以先做局部组件测量，但最终仍要用真实整页输出复核，因为局部放得下，不代表与邻近模块没有冲突。

另外：

> **文字边界装进框里，不等于实际尺寸下可读。**

最小字号、地图细节密度和阅读条件仍需要明确的项目要求；自动检测不了的项目，应标记需要人工检查，不能统一视为通过。

### 5. 此阶段先“发现问题”，不急于“自动修好”

建议第二阶段的最小闭环是：

```text
固定布局
→ 测量
→ 渲染
→ 检查
→ 明确通过或明确不适配
```

可以支持已定义的普通换行，但不要立即引入任意改框、删内容和缩字。

### 阶段二的验收标准

- 标题变长时，报告真实行数和容量问题；
- 图例标签变长，即使条目数不变，也能发现尺寸变化；
- 来源换成较长内容时，不被静默截断；
- 更换字体后，旧测量结果失效；
- 测量与实际绘制明显不一致时，不能冻结。

**这一阶段完成后，系统可以不够灵活，但必须诚实地知道“装不下”。**

## 四、阶段三：增加少量候选，以及有边界的修订循环

### 目标

有了可靠测量之后，再解决：

> **当前布局不合适时，在允许范围内尝试什么，什么时候停下来交给人。**

### 1. 先登记有限变体，不做任意自由布局

例如，在兼容且已批准使用的布局中允许：

- 右侧图例；
- 底部图例；
- 单行标题区；
- 双行标题区；
- 图例单列或双列。

这些变体的前提、尺寸范围与约束要有明确协议。

不要让模型直接提交任意坐标脚本，也不要让它临时发明未经验证的排版方法。

### 2. 候选必须保持相同的内容与表达语义

比较两个布局时应保持：

- 相同必保内容；
- 相同数据；
- 相同分类含义；
- 相同输出条件；
- 相同强制声明。

不能通过删掉图例类别或缩小到不可读，获得一个表面上更宽松的候选。

允许改变的只是已经授权的几何或排布参数。

### 3. 每个候选拥有独立身份和证据

当前流程主要围绕一份候选文件工作。要支持候选比较，需要同步调整：

- 候选的唯一标识；
- 不可变候选存储；
- 每个候选的测量、预览与检查引用；
- 当前选中候选的明确记录；
- G2 对选中候选的精确绑定。

**不能用多个方案反复覆盖同一份候选，再沿用旧回执。**

现有 `ResolvedMap` 和 `MapSpecLock` 已共享执行快照定义，可以在这条链上增加严格类型的布局结果与测量引用，而不是另外创建一套冻结体系。参见 [候选协议](skills/carto-agent/schemas/resolved-map.schema.json)、[现有锁的快照绑定](skills/carto-agent/scripts/carto_core/compiler/map_lock.py#L76)。

### 4. 先检查硬约束，再比较质量

建议顺序：

```text
过滤不可行候选
  ├─ 必保内容缺失
  ├─ 越界或非法重叠
  ├─ 低于已确认的可读条件
  └─ 违反人工锁定或语义约束

比较剩余候选
  ├─ 地图可用空间
  ├─ 内容区容量余量
  ├─ 对齐与间距
  └─ 相比已确认布局的变动程度
```

这里不必急于设计一个综合“审美分”。早期采用可解释的优先级排序，往往比权重不清的评分更容易审核。

只有一个可行方案就如实展示一个，不需要为了凑数生成几乎相同的候选。

### 5. 用结构化修订替代无限重试

修订请求可以表达为：

```text
对象：legend-frame
问题：图例高度不足
动作：切换到已允许的双列变体
依据：当前测量报告
影响：重新测量图例并复查相邻地图区域
```

程序负责验证该动作是否在授权范围内。

以下变化不能作为普通布局修复：

- 删除必保内容；
- 改分类数、单位或统计口径；
- 裁掉必保地理范围；
- 缩小到确认的字号下限以下；
- 改变已批准的用途或输出条件。

这些应返回内容或地图规划，并触发适用的重新确认。

### 6. 设置停止条件

至少包括：

- 达到候选数量或修订预算；
- 连续修订没有改善；
- 所有已登记变体都不适配；
- 下一步需要改变内容或输出条件；
- 工具结果不足以确认可行性。

同时区分：

- “现有这些变体没有找到可行结果”；
- “已经证明约束不可行”；
- “预算耗尽，尚未确定”。

三者不能混为一谈。

### 阶段三的验收标准

例如，一段较长标题和较多图例进入系统：

1. 原布局测量失败；
2. 系统尝试已登记变体；
3. 每个候选都保留完整内容；
4. 展示通过情况和取舍；
5. 人工确认精确候选；
6. 冻结后不再自动变更。

这时才算真正具备了**有限但可信的自动布局适配**。

## 五、阶段四：扩展到复合专题页的模块关系与布局求解

### 目标

这一阶段才从“标题、图例围绕一幅地图排布”，扩展为：

> **多张地图、图表、指标和文字共同竞争页面空间，并依据内容关系确定位置。**

### 1. 把内容模块需求纳入现有规划协议

建议扩展现有 `MapPlan` 等类型化输入，表达：

- 模块回答的问题；
- 优先级和是否必保；
- 内容及数据引用；
- 所属主题组；
- 标题、图例、单位、来源等随行元素；
- 允许的表现变体；
- 相邻、上下、对齐关系；
- 调整权限与人工锁定。

这对应参考材料的“模块需求卡”，但不必机械增加一份与现有计划并列的权威 `ContentPlan`。

### 2. 每种模块都应能够测量、绘制和检查

例如：

- 指标卡：名称、数值、单位的组合测量；
- 名单：单列、双列及长名称换行测量；
- 统计图：轴标、图例、类别名称与绘图区测量；
- 地图：地图框、注记、图符与局部说明检查。

特别要注意：

> **外框不重叠，只能证明模块之间的几何关系，不能证明地图内部的标签、引线与符号没有冲突。**

内部检查与整页布局检查需要分层处理。

### 3. 多地图能力必须先于完整复合页承诺

当前 `RenderScene` 以单个地图对象和相机为核心。支持主图、辅图、区位图，不是只增加几个矩形：

- 需要多个视图各自的数据和空间上下文；
- 各自的相机、地图框和图例归属；
- 多视图资源与渲染证据；
- 对应的场景能力登记和语义检查。

因此建议先扩展：

> 一幅地图＋一个简单统计组件或指标区。

待其稳定后，再加入第二幅地图、名单和复杂专题模块。

### 4. 先分组和选骨架，再求几何

不要从“把所有模块当矩形一起塞满页面”开始。

更合理的顺序是：

```text
内容需求与关系
→ 主题分组
→ 少量整页骨架
→ 根据实测需求分配区域
→ 组内排列
→ 真实渲染
→ 联动复查
```

初期仍可以枚举少量栏宽与变体。只有模块数量、约束复杂度和交互锁定需求增长后，再评估通用约束求解器。

### 5. 建立变更依赖

例如：

```text
企业名称变长
→ 名单重新测量
→ 中栏空间需求变化
→ 相邻地图框可能变化
→ 地图重新适配和注记检查
→ 整页重新验证
→ 相关批准重新确认
```

依赖追踪的目的不是只追求少算一点，更重要的是**避免更新了局部内容，却继续使用已经不适用的布局与批准**。

## 六、建议的实际实施顺序

不建议四阶段同时展开。可以按以下顺序逐步交付：

| 批次 | 工作范围 | 明确暂不做 |
|---|---|---|
| 第一批 | 固定 Frame 解析、完整元素绑定、实际渲染消费、统一边界检查 | 自动换布局、复杂文本测量 |
| 第二批 | 标题/图例/来源真实测量，换行与容量报告 | 任意自动修订 |
| 第三批 | 两三种登记变体、候选证据、受控回调、精确选择与冻结 | 多模块通用求解 |
| 第四批 | 单主图＋简单统计组件，模块需求与关系 | 一次性复刻十一模块案例 |
| 后续 | 多视图、名单、复杂注记、局部重排与更强求解 | 未经验证的全面生产能力声明 |

所有批次都应坚持：

- 实现仍在 `skills/carto-agent/`；
- 新协议提供合法、非法样例及自动测试；
- 新字段使用严格 Schema，不把布局结构随意塞入自由字段；
- 已发布模板、候选和锁不原地覆盖；
- 协议或策略变化不能靠自动兼容旧锁继续执行；
- 验证能力增强与业务能力开放分别管理。

## 最重要的取舍

**我建议下一步只把第一、第二阶段作为近期目标。**

它们完成后，即使系统仍只有一个固定布局，也已经实现了一个很有价值的变化：

> 从“代码把元素放到几个固定坐标，最后大致检查边界”，升级为“契约决定位置，真实内容决定是否适配，证据决定能否冻结”。

有了这个基础，第三阶段的候选搜索才不会只是在不可靠的尺寸估计上反复试错；第四阶段的复杂布局也才有可复用的组件和约束基础。
