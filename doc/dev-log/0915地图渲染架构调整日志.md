## 调整演进脉络

本文档经历了三轮迭代：

| 轮次 | 核心命题 | 结论 |
|---|---|---|
| 第一轮 | 将 QGIS 适配器替换为 MapLibre + Canvas 前端渲染器 | 建立稳定的 RenderScene 合同，后端做决策，前端做呈现 |
| 第二轮 | 对比 PPT Master 架构，确认是否需要后端渲染 | 地图必须栅格化，但不需要自研后端渲染引擎；需要受控无头浏览器渲染服务 |
| 第三轮 | 如果产物需要要素级编辑，应该用什么格式 | overlay 用 SVG 矢量元素，产物为可编辑 SVG，轻量合成器拼接 |

三轮迭代的最终结论：**不是"把 QGIS 换成 MapLibre"，而是建立 RenderScene → 无头浏览器渲染 → SVG 合成 → 可编辑产物的完整确定性管线。**

## 一、核心架构调整

### 1. 将前端页面定位为 Executor

当前的 Strategy/Executor 两层仍然成立：

| 层次 | 主要职责 |
|---|---|
| Strategy | 理解制图意图、选择模板、绑定数据、确定分类方法、范围、符号语义和版面 |
| Compiler | 将地图计划编译成确定性的 RenderScene |
| Frontend Executor | 使用 MapLibre 和 SVG 还原 RenderScene |
| Validator | 检查语义、资源、渲染效果和输出成果 |
| SVG Compositor | 将地图截图与 SVG overlay 合成为可编辑 SVG 产物 |

前端执行器不能自主决定：

- 分类字段和分类断点；
- 哪些数据进入地图；
- 数据值与符号的映射关系；
- 图层是否代表观测、预测或推断数据；
- 模板硬规则是否可以忽略；
- 地图范围、输出尺寸和正式成果参数。

它只负责忠实执行已编译的场景。

### 2. 不再单独建设 Layout Compositor，改为 SVG 合成器

原建议中存在一个独立的 `layout_compositor.py`。经分析，版面合成应在前端通过 SVG overlay 元素完成，后端只需要一个轻量合成器将地图截图与 overlay 拼接为最终 SVG。

```
（原方案）
MapLibreRenderer → LayoutCompositor → PNG/PDF

（调整后）
前端渲染执行器
├─ MapLibreHost           ← WebGL 地图渲染（必然栅格）
├─ SvgOverlayEngine       ← SVG/HTML 矢量叠加元素（图名/图例/指北针等）
├─ SceneCoordinator       ← 协调两者刷新与投影
└─ ExportController       ← 预览截图 + 正式导出
         ↓
后端 SVG 合成器（~300 行）
├─ 嵌入地图截图为 <image>
├─ 追加 SVG overlay 元素（保持矢量）
└─ 内联字体/图标资源
         ↓
可编辑 SVG 产物
```

### 3. 适配器命名

推荐使用：**`WebMapRendererAdapter`**

实现标识记录为：

```
renderer_id: maplibre-canvas
```

这样未来即使 MapLibre 版本或前端框架改变，内部协议也不需要重新命名。

> **命名修正**：原建议中"CanvasOverlayEngine"应改为"SvgOverlayEngine"。overlay 必须用 SVG/HTML 元素实现而非 `<canvas>` 位图绘制，这是从"终端栅格产物"升级为"可编辑矢量产物"的唯一前提。

## 二、需要新增统一的 RenderScene 协议

后端不能直接向前端发送零散的 MapLibre 配置和绘图命令。建议编译成一个统一的、不可执行的类型化场景协议。

```json
{
  "schema_version": 1,
  "scene_id": "scene-flood-001",
  "renderer_id": "maplibre-canvas",
  "viewport": {
    "width_px": 1684,
    "height_px": 1191,
    "device_pixel_ratio": 2,
    "background": "#FFFFFF"
  },
  "camera": {
    "bounds": [112.1, 28.0, 114.2, 29.8],
    "bearing": 0,
    "pitch": 0,
    "padding": { "top": 80, "right": 320, "bottom": 90, "left": 80 }
  },
  "map": {
    "style_ref": { "id": "flood-style", "version": "1.0.0", "digest": "sha256:..." },
    "sources": [],
    "layers": []
  },
  "overlays": [
    {
      "id": "map-title",
      "type": "text",
      "coordinate_space": "page",
      "position": { "x": 0.05, "y": 0.04 },
      "content": "洪涝灾害风险专题图",
      "style_role": "map-title"
    },
    {
      "id": "survey-point-01",
      "type": "symbol",
      "coordinate_space": "geographic",
      "anchor": { "longitude": 113.1, "latitude": 28.7 },
      "symbol_ref": "survey-location",
      "label": "调研点一"
    }
  ],
  "export": {
    "targets": ["svg", "pdf", "png"],
    "dpi": 300
  }
}
```

> **关键修正**：`export.targets` 增加 `svg` 作为首要产物格式。`svg` = 可编辑矢量产物，`pdf` = 从 SVG 转换的混合质量文档，`png` = 纯栅格预览图。

这个协议应该成为前后端唯一的地图渲染合同。

> **Schema 约束**：RenderScene 的字段要严格用 `additionalProperties: false`，overlay 类型用 `enum` 限定（text/symbol/legend/north-arrow/scale-bar/attribution/complex-symbol），不要留开放式 `type: string`。

## 三、必须区分四种坐标空间

因为 overlay 同时承载版面元素和地图专题符号，所以坐标系统是这套架构最关键的部分。

建议每个 overlay 元素必须声明 `coordinate_space`：

| 坐标空间 | 用途 | 示例 |
|---|---|---|
| `page` | 相对整张制图页面固定 | 图名、数据来源、Logo、页码 |
| `viewport` | 相对地图视口固定 | 图例、比例尺、指北针 |
| `geographic` | 随地图缩放和平移 | 调研点、灾害点、线路箭头、专题标记 |
| `feature` | 绑定到某个地图要素 | 行政区名称、重点企业标记、设施标注 |

其中：

- `page` 建议采用 0～1 的归一化坐标。
- `viewport` 可采用像素或归一化坐标。
- `geographic` 使用经纬度或规范化坐标。
- `feature` 使用 `source_id` + `feature_id` + `anchor_rule`。

不能只保存最终屏幕上的 x/y。否则地图缩放、平移或改变输出尺寸后，专题符号会与地图错位。

## 四、Overlay 技术选型：SVG 而非 Canvas 位图

这是第二轮分析中最重要的修正。

### 问题

原建议中 overlay 引擎命名为"CanvasOverlayEngine"，暗示用 `<canvas>` 2D context 绘制标题、图例、指北针等。但 `<canvas>` 的内容本质上是一张位图——无论怎么导出都是栅格的。

### 影响

| overlay 实现方式 | Chrome headless `page.pdf()` 输出 | 文字质量 | 要素可编辑性 |
|---|---|---|---|
| `<canvas>` 2D context | overlay 是栅格 | 放大有锯齿 | 不可单独编辑 |
| SVG / HTML 元素 | overlay 文字是**矢量** | 无限缩放不失真 | 每个元素可单独选中编辑 |

### 决策

overlay 必须用 **SVG / HTML DOM 元素**实现，不能用 `<canvas>` 位图绘制。这样：

1. **Chrome headless `page.pdf()` 自动产出混合质量 PDF**：地图栅格 + overlay 矢量文字
2. **SVG 合成器可提取 overlay 元素**：overlay 在 DOM 中是 SVG 节点，直接拷贝到产物 SVG
3. **要素级编辑**：每个 overlay 元素是独立 DOM 节点，有 `id`，可被浏览器/Inkscape/Illustrator 选中编辑

```
前端渲染执行器
├─ MapLibreHost          → <canvas> (WebGL 地图，必然栅格)
├─ SvgOverlayEngine     → SVG/HTML 元素 (标题/图例/指北针，矢量)
├─ SceneCoordinator     → 协调两者
└─ ExportController
    ├─ 预览：截图
    └─ 正式：headless Chrome 渲染 → 地图截图 + SVG overlay → 合成器
```

## 五、前端需要增加 SceneCoordinator

MapLibre 和 overlay 不能各自独立刷新，需要有一个统一协调器：

```
SceneCoordinator
├─ 加载 RenderScene
├─ 初始化 MapLibre 地图
├─ 等待底图和专题图层稳定
├─ 获取统一相机和视口状态
├─ 投影 geographic/feature 锚点到屏幕坐标
├─ 更新 SVG overlay 元素的 transform 属性
├─ 检查字体、图标和瓦片资源
└─ 通知 ExportController 可以导出
```

需要处理的前端事件包括：

- 地图初始化完成；style 加载完成；source 数据完成；
- 字体和图标加载完成；
- 地图平移、缩放、旋转；页面 resize；
- 地图进入稳定状态；导出尺寸或 DPI 改变。

对地理锚定的 overlay 元素，每次地图相机变化时都需要重新计算屏幕位置并更新 SVG 元素的 `transform` 属性。

> **后端边界说明**：SceneCoordinator 是纯前端实现，后端不需要知道其存在——后端只发 RenderScene、收 RenderReceipt。SceneCoordinator 属于前端工程范畴，不进 Schema 和策略文件。

## 六、明确 MapLibre 和 Overlay 的职责边界

### MapLibre 负责

- 底图；行政区面；河流、道路等连续线要素；
- 面分级设色；普通点、线、面专题图层；
- 需要随缩放裁切的图层；
- 地图范围、缩放、旋转和视口；
- 可交互查询的业务要素。

### SVG Overlay 负责

- 图名、副标题；图例；指北针；比例尺；
- 数据来源和署名；页边信息；
- 自定义复杂符号；调研点标记；
- 路线装饰和特殊箭头；领导批示、重点标注和引线；
- 需要精确页面布局的注记；
- MapLibre 样式难以表达的复合专题符号。

不能让同一个语义图层同时由 MapLibre 和 overlay 分别决定样式。例如"洪涝风险等级"如果由 MapLibre 绘制面分级设色，图例必须读取同一份编译后的分类和颜色定义，不能在 overlay 中重新计算。

## 七、模板系统需要怎样调整

现有四类模板不需要增加第五类。

### MapBrand

同时输出 MapLibre 和 SVG overlay 共用的身份 Token：

- `color.primary` / `color.accent`
- `font.title` / `font.label` / `font.legend`
- `logo.asset`
- `attribution.style`

### MapStyle

定义制图语义和符号映射，但不直接保存任意 JavaScript：

- 分类方法；颜色映射；图层顺序；标注规则；
- 点线面表达；SVG overlay 符号角色；MapLibre layer 类型映射。

### MapLayout

主要由 SVG overlay 消费：

- 页面尺寸；地图视口区域；标题区域；图例区域；
- 指北针位置；比例尺位置；数据来源位置；安全边距；附图区域。

已有的 frames 继续使用，但增加：

- `coordinate_space` / `z_index` / `clip` / `responsive_behavior` / `visibility_condition`

### MapScenario

负责组合：MapLibre 图层集合；SVG overlay 元素集合；数据角色；页面结构；输出目标；场景特有规则。

## 八、协议层建议只新增两个主要协议

### 1. `render-scene.schema.json`

描述前端需要渲染的完整确定性场景：viewport；camera；MapLibre style/source/layer；SVG overlay；坐标空间；资源引用；输出参数（含 svg 目标）；环境要求；场景摘要。

### 2. `render-receipt.schema.json`

前端完成渲染后返回：`scene_digest` / `renderer_id` / `frontend_build_version` / `maplibre_version` / `overlay_engine_version` / `browser_version` / `viewport` / `device_pixel_ratio` / `loaded_asset_digests` / `missing_assets` / `warnings` / `preview_artifact_ref` / `render_started_at` / `render_completed_at` / `renderer_attestation`。

> `renderer_attestation` 记录前端构建版本的签名摘要，后端校验前端构建版本是否在可信列表中。

不需要为标题、图例、指北针分别创建独立协议。它们作为 `render-scene.overlays[]` 的类型化节点即可。

## 十、适配器层需要怎样调整

原来的 `QgisEnvironmentProbe` / `QGISAdapter` / `Renderer` 建议改成：

```
WebMapRendererAdapter
RendererCapabilityRegistry
RenderSessionGateway
RenderReceiptValidator
SvgCompositor（轻量合成器）
```

`WebMapRendererAdapter` 不负责实际绘图，而负责：

1. 校验前端渲染器是否已注册；
2. 校验其版本和能力；
3. 下发 RenderScene；
4. 接收 RenderReceipt；
5. 校验场景摘要是否一致；
6. 触发 SVG 合成器生成最终产物；
7. 将回执写入步骤记录。

前端页面是实际执行器，后端 Adapter 是可信边界和协议桥梁。

## 十一、环境探测应改为前端能力握手

现有 `qgis_probe.py` 不应简单改成检查本机是否安装 MapLibre。

因为 MapLibre 实际运行在前端页面中，后端本地环境探测不能代表用户浏览器。

更合适的是前端启动后提交：

```json
{
  "renderer_id": "maplibre-canvas",
  "frontend_build": "2026.09.15",
  "maplibre_version": "...",
  "overlay_engine_version": "...",
  "browser_engine": "...",
  "webgl_available": true,
  "supported_exports": ["svg", "png"],
  "max_canvas_size": { "width": 16384, "height": 16384 },
  "device_pixel_ratio": 2,
  "available_fonts": ["Microsoft YaHei"],
  "offline_rendering": true
}
```

后端校验后形成环境指纹。如果未来部署受控的无头导出服务，也使用完全相同的能力握手协议。

> **安全约束**：前端提交的能力清单是自报的，不能直接信任——后端需要对其做范围校验（DPR 不能超过 4，max_canvas_size 不能超过已知上限）。

## 十二、预览和正式出图要分开

### 浏览器交互预览

用于：查看地图；调整范围；拖动图例；调整专题标注；查看候选效果；形成 G2 审批前预览。

浏览器中的人工调整不能直接修改冻结结果。调整应生成类型化变更：`move-overlay` / `resize-overlay` / `change-camera` / `toggle-layer` / `update-label-anchor`。这些变更回传后端，产生新的候选版本。

### 受控正式输出（必须，非可选）

企业级生产**必须**使用受控无头浏览器，这不是可选项：

```
同一个前端渲染包
    ↓
受控无头 Chrome 加载
    ↓
读取冻结后的 RenderScene
    ↓
渲染地图（WebGL 截图）+ 渲染 overlay（SVG DOM）
    ↓
SVG 合成器拼接
    ↓
可编辑 SVG 产物
```

**为什么必须用无头浏览器而非用户浏览器**：

| | 用户浏览器（预览） | 受控无头 Chrome（正式） |
|---|---|---|
| 浏览器版本 | 不可控 | 固定版本 |
| DPR | 不可控（1~3） | 固定值 |
| 字体 | 不可控 | 固定字体集 |
| WebGL 实现 | 不可控 | 固定 |
| 可信度 | 不可信（可被篡改） | 可信 |
| 可重放性 | 不保证 | 保证（同 RenderScene → 同像素） |

当前 `MapSpecLock` 的 `execution_digest` 机制要求冻结后输入不变，确保可重放。但如果渲染发生在用户浏览器，相同输入不保证相同输出。只有受控无头浏览器能保证确定性。

## 十三、输出格式与合成策略

### 产物格式决策

| 格式 | 定位 | 地图部分 | overlay 部分 | 要素可编辑 |
|---|---|---|---|---|
| **SVG** | **首要产物** | 嵌入为 `<image>`（栅格） | SVG 矢量元素 | 是 |
| PDF | 从 SVG 转换 | 栅格 | 矢量文字 | 需 Illustrator |
| PNG | 纯预览 | 栅格 | 栅格 | 否 |

**SVG 作为首要产物的理由**：

1. overlay 元素本身就是 SVG，合成器只需拼接，无需格式转换
2. 每个元素有 `id`，可被浏览器/Inkscape/Illustrator 选中编辑
3. 地图画面嵌入为 `<image>`（栅格），不可编辑但也不需要编辑——改地图应回后端重新编译
4. SVG → PDF/PNG 是简单转换，不需要写编译器

### SVG 合成器（后端，约 300 行）

合成器逻辑本质上是拼接 + 资源内联：

```python
def compose_svg(render_scene, map_screenshot_path, overlay_elements) -> str:
    # 1. 地图截图嵌入为 <image>
    # 2. overlay 元素已经是 SVG，直接追加（保持矢量）
    # 3. 内联字体和图标资源
    # 4. 输出自包含 SVG
```

对比 PPT Master 的 svg_to_pptx 编译器（13000+ 行），Carto Agent 的合成器极轻，因为：

| | PPT Master svg_to_pptx | Carto Agent SVG 合成器 |
|---|---|---|
| 做什么 | SVG → DrawingML 跨格式转换 | SVG 片段 + 栅格图 → 单个 SVG 文件 |
| 元素映射 | 5322 行（每个标签 → DrawingML 对象） | 零（SVG 元素就是 SVG 元素） |
| 复杂度 | 高（跨格式、跨对象模型） | 低（同格式拼接 + 资源内联） |

## 十四、后端渲染的三个层次

| 类型 | 含义 | 是否需要 | 理由 |
|---|---|---|---|
| **A. 后端渲染引擎** | 自己写代码画像素 | 不需要 | MapLibre 是成熟引擎，重写等于重写 MapLibre |
| **B. 后端渲染服务** | 受控环境跑同一个前端引擎 | **必须** | 可重放性、可信度、批量生成的硬要求 |
| **C. 后端格式编译器** | 把中间语言转成目标格式 | 轻量版需要 | SVG 合成器（~300 行），非 PPT Master 式重编译器 |

PPT Master 只需要 C（格式编译器），不需要 B（渲染服务），因为 PPTX 是编译出来的，不是渲染出来的。

Carto Agent 的地图必须渲染（WebGL 像素），所以需要 B（无头浏览器渲染服务）。但因为目标是 SVG 而非 PPTX，所以 C 是轻量合成器而非重编译器。

---

## 十五、验证体系需要增加的检查

### 场景静态校验

- 所有 MapLibre source 和 layer ID 唯一；
- SVG overlay 节点引用的符号和字体存在；
- 图例读取的分类、颜色和符号与专题图层一致；
- 地理锚点合法；
- 页面元素没有越过安全区；
- 图层和 overlay 的 z-index 没有冲突；
- 不允许任意 JavaScript 绘图代码。

### 前端预检

- MapLibre style 已加载；source、瓦片、sprite、glyph 已加载；
- SVG overlay 字体和图标已加载；
- 所有地理符号已成功投影；
- 无缺失资源；输出尺寸受支持；前端版本与场景要求匹配。

### 产物校验

- SVG 产物中每个 overlay 元素有唯一 `id`；
- 地图 `<image>` 的 digest 与渲染回执一致；
- 内联资源（字体、图标）完整无缺失；
- SVG 可被标准解析器（`xml.etree`）无错打开。

## 十八、PPT Master 对比与借鉴

### 架构对比

| | PPT Master | Carto Agent 调整方案 |
|---|---|---|
| 中间语言 | SVG（W3C 标准） | RenderScene JSON（自定义协议） |
| 前端渲染 | 浏览器原生 SVG 渲染 | MapLibre + SVG overlay |
| 后端编译器 | svg_to_pptx（13000+ 行，跨格式） | SVG 合成器（~300 行，同格式拼接） |
| 后端渲染服务 | 不需要（PPTX 是编译的） | 需要（地图必须渲染，无头浏览器） |
| 最终产物 | .pptx（矢量 DrawingML，可编辑） | .svg（矢量 overlay + 栅格地图，可编辑） |
| 前端预览 | 辅助、可选 | 主要预览方式 |
| 正式输出来源 | 后端编译器（权威） | 后端无头浏览器 + SVG 合成器 |

### 可借鉴的 5 个设计模式

1. **前端标注 → 类型化变更 → 回传后端的闭环**：PPT Master 的 annotation 系统验证了此模式。Carto Agent 的 `move-overlay` 等变更回传是同一模式的升级版（从自由文本到结构化变更）。

2. **预览 ≠ 正式输出的明确边界**：PPT Master 硬规则"the editor never runs the export pipeline"。Carto Agent 应在策略文件中写死"前端不执行正式导出"。

3. **SVG 作为中间语言**：PPT Master 证明 SVG 既能浏览器原生渲染，又能后端解析编译。Carto Agent 的 overlay 直接用 SVG 获得了同样的双重优势。

4. **finalize 步骤**：PPT Master 的 `finalize_svg.py` 生成自包含 SVG。Carto Agent 的 SVG 合成器也应有 finalize 步骤，确保所有资源内联。

5. **编译器 = 确定性管道**：PPT Master 的 svg_to_pptx 是纯确定性的，没有模型参与。Carto Agent 的 RenderSceneCompiler 和 SVG 合成器也应如此。

### 根本差异：目标格式

PPT Master → 目标是 PPTX（DrawingML XML），必须写编译器把 SVG 转成 DrawingML。

Carto Agent → 目标是 SVG（本身就是中间语言），不需要跨格式编译。Chrome 自带 PDF 引擎，SVG → PDF 是简单转换。

**所以 Carto Agent 不需要 PPT Master 那样的 13000 行后端编译器。它需要的是无头浏览器渲染服务 + 轻量 SVG 合成器。**

## 评估总结

| 维度 | 评分 | 说明 |
|---|---|---|
| 架构兼容性 | 高 | 不改五模块、不改安全底座、不改四类模板、不改审批门禁。新增的 RenderScene、render-receipt 和 SVG 合成器是现有协议体系上的自然延伸。 |
| 改动控制力 | 高 | 后端改动集中在 adapters 层 + 2 个新 Schema + environment-fingerprint 泛化 + SVG 合成器（~300 行）。核心模块零改动。 |
| 安全一致性 | 高 | 正式输出走受控无头浏览器，确保可重放。render-receipt 有 `renderer_attestation` 字段防篡改。SVG 合成器在后端可信环境运行。 |
| 产物质量 | 高 | SVG overlay 矢量化解决了原方案"栅格 PDF 质量降级"风险。文字无限缩放不失真，每个 overlay 元素可单独编辑。 |
| 可演进性 | 高 | `renderer_id: maplibre-canvas` 允许未来换引擎不改协议。SVG 产物格式是开放标准，不绑死任何工具。 |
| 实现复杂度 | 中 | SceneCoordinator、SVG overlay 投影、无头浏览器服务是前端工程复杂度。后端 SVG 合成器极轻（~300 行）。 |

**总体判断：建议合理，可采纳。** 落地时的关键约束是：

1. overlay 必须用 SVG/HTML 元素，不能用 `<canvas>` 位图——这是矢量产物和栅格产物的分水岭；
2. 正式输出必须走受控无头浏览器——这是可重放性和可信度的硬要求；
3. RenderScene Schema 严格封闭（overlay 类型用 enum、`additionalProperties: false`）；
4. SVG 合成器在后端运行，产出自包含 SVG，再按需转 PDF/PNG。
