## 一、目标与实施边界

**目标：使已经批准、经过验证的制图规则能够被新任务正确复用；不适用时拒绝或澄清，规则失效时停止错误复用，并保留历史证据。**

完整链路为：

> 原始材料 → 可追溯规则 → T1 批准 → 确定性模板 → 验证 → TP 发布 → 任务适用性检查 → 获准实例调整 → 地图冻结与交付 → 问题归因 → 修订或停止使用。

本计划只加深这条链，不扩大为通用模板平台。

### 1.1 固定约束

1. 保留 `analyze → brief → author → validate → publish`，以及地图生成既有工作流；不新建平行路由或地图实现。
2. 保留四类模板及其职责。首轮聚焦 MapScenario 的受控作者与已有内嵌段，不同时开放 Brand/Style/Layout 独立作者。
3. LLM 提出语义设计；程序验证与机械推导；人工确认业务含义并作必要专业审查。能力、安全与数学约束不得以设计自由为由移除。
4. 模板持有稳定规则、默认值、适用前提与可调范围；项目持有真实数据、地点、时间、范围和数据驱动结果。固定业务阈值可以通过规则或标准引用约束，不能一律视为实例随机值。
5. T1/TP 与 G1/G2/G3 不混用；管理处置必须定义自己的动作、对象和授权，不能借用既有 gate 冒充授权。
6. 所有外部路径先过允许根校验；不把原始业务行、完整行程、敏感坐标或密钥放入普通日志、模板包和仓库 Fixture。
7. 新协议同步修改生产者、消费者、正反例和说明；不增加旧格式 wrapper，不修改已发布包或旧锁来“迁移”。
8. 真实任务验收和生产准入分别决定。本计划完成任何工程阶段，都不自动设置 `production_enabled: true`。

## 三、阶段总览、依赖与优先级

优先级不是预计工期：P0 防止错误成功，P1 支持安全复用与演进；场景接入按材料与业务时限条件决定。不编造人日或承诺日期，TM-0 后按实际改动与可用人员排期。

| 批次 | 优先级 | 用户获得的能力 | 前置条件 | 主要退出证据 |
|---|---|---|---|---|
| TM-0 基线与验收样本确认 | P0，先消除不确定性 | 明确先做什么、凭什么验收 | 已授权调查范围 | 范围、证据缺口、责任和最小合同决策已确认 |
| TM-1 获批设计真正生效 | P0 | 批准的规则确实影响模板和地图 | TM-0 的合同与版本边界确定 | 设计差分、确定性、越权拒绝及一个完整消费闭环 |
| TM-2 适用性与复用验证 | P0 | 新任务适用时成功，不适用时正确停止 | TM-1；获准主样本和留出材料 | 正常/合法边界/超界/缺证据案例，真实留出任务及独立审查 |
| TM-3 最小发现与生命周期治理 | P1；严重事件时上调 P0 | 能找到模板、解释状态、停止问题版本并定位影响 | 3A 可在 TM-0 后开始；3B 依赖 TM-1/2 的合同和证据语义 | 只读查询、精确处置、既有运行行为及恢复演练 |
| TM-4 受控多模板与多版本 | P1 | 同一受信能力服务多个经过验证的模板 | TM-1/2、TM-3 的处置与版本规则 | 不复制业务代码的两个合法资产，新旧版本隔离与准入负例 |
| TM-5 三场景逐项验收与反馈 | 条件性接入，逐项决定 | 各场景有完整、受控的真实任务闭环 | 对应业务组件和数据证据就绪；推广复用前完成治理 | 各场景独立证据包、反馈处置与准入决定 |

主实施依赖：`TM-0 → TM-1 → TM-2 → TM-3B → TM-4`。

- TM-3A 的只读视图可提前，不能为等待推荐算法拖延它。
- 三场景材料收集从 TM-0 开始；TM-2 已做首个真实复用验收，不把真实任务全部推迟到 TM-5。
- TM-5 不要求所有场景同步开工或同时完成；只依赖该场景实际需要的前序能力。只有需要多模板/多版本时，TM-4 才是其硬前置。
- 若真实严重错误或授权失效已发生，应立即停止受影响操作，将最小处置前移；不得等待整套 TM-3 完成才止损。

## 四、阶段任务与验收

### TM-0：确认基线、样本与最小合同（P0）

**目标：**把讨论中的判断转换为可以开发、可以推翻的范围和验收依据。

**任务**

1. 重新核对工作区、代码版本、当前准入、协议与消费者；把“已实现”“可调用”“已测试”“已真实验收”分列。
2. 按仓库入口确认真实 Python 3.11+，再运行唯一 CLI 的 `--help`、`schema check`。渲染探测和开发测试按授权执行；记录跳过与缺依赖，不自动安装。
3. 确认一份用于设计的主样本及一份不参与作者调试的留出材料，登记授权、来源与元数据；取得原始任务和审校要求。合成数据只用于技术回归。
4. 将“标题字号决定变化但作者输出不变”的历史对照固化为回归；同时明确该字段在现协议里是否仅是记录，不能把记录字段冒充已支持设计。
5. 冻结三项最小决策：执行设计字段及所有权；模板/实例变化边界；对应协议与模板版本的协调切换范围。
6. 分别指定技术合同负责人、业务语义确认人、独立审查/审批职责。独立于作者不等于多起一个 LLM；真实审批仍由受信身份验证。

**材料选择**

| 场景 | 候选材料与开工条件 | 本阶段不能声称的结论 |
|---|---|---|
| 标准专题 | 已有土地覆盖文件可列为候选；必须先确认类别语义、来源和授权 | 不根据文件名认定数据正确或适用；保护等级混合 NoData 的记录只能作反例线索 |
| 政务专题 | 取得任务书、指标/分母/单位、时间和区划版本、审校要求 | 现有州级指标图按 general 场景运行，不等于政务验收 |
| 领导调研 | 取得获准的地点、访问顺序、路线性质和披露要求 | 无材料不模拟成已验收；不把旧分支算法当作已接入能力 |

**交付与退出：**范围与非目标、规则—证据—消费者表、合法/非法验收清单、版本切换决定、人员责任均明确；未决项标明会阻断哪一步。缺真实材料可以继续无依赖的工程工作，但不能关闭真实验收项。

**失败处理：**调整最小范围或补材料；不靠扩大场景、修改生产开关或虚构数据消除缺口。

### TM-1：打通获批设计到成品的消费链（P0）

**目标：**模板不再只是固定代码声明的包装；同时避免把所有设计参数一次开放。

**分三个可检查切片实施**

| 切片 | 工作 | 协议/代码范围 |
|---|---|---|
| 1A 设计与证据分离 | 在既有请求/简报中定义严格的可执行设计；区分来源事实、建议、用户决定与缺项；复用现有契约定义 | `S/template-create-request.schema.json`、`S/general-template-create-request.schema.json`、`S/template-analysis.schema.json`、`S/template-brief.schema.json`；`C/workflow/template_analysis.py`、`template_brief.py` |
| 1B 作者确定性展开 | 作者只消费已批准设计及固定依赖；缺设计项拒绝，不以代码偏好补全；人读说明不得成为第二执行权威 | `C/workflow/template_author.py`、`template_workflow.py`；`C/scenarios/general_thematic.py`、`general_vector.py`；按需联动 `C/repository/staging_package.py` |
| 1C 应用解析与核验 | 记录原模板、获准实例调整与有效值来源，复用既有修订/候选/冻结链；只开放经过验证的参数 | `C/workflow/map_generation.py`；`C/compiler/map_candidate.py` 及实际受影响的布局、外观、页面消费者 |

1A 的单独 Schema 改动不是可发布阶段：对应生产者、消费者和正反例必须协调完成。首个闭环可使用一个显式登记的新模板版本，不要求先完成 TM-4 的泛化；不能覆盖 `3.0.0/4.0.0` 等已发布内容，也不能新增旧协议自动迁移分支。

**验收**

- 合法：改变一个已开放的设计值，简报、对应模板合同、有效设计及真实成品出现预期变化；不相关语义保持。
- 合法：相同冻结输入得到相同执行语义和内容；时间戳、签名等变化单独对待，不能用去除绑定的方式追求相同摘要。
- 非法：未知设计字段、未经批准的字段覆盖、缺少必需设计、以新设计复用旧 T1 均拒绝。
- 应用：允许范围内的项目调整不改变已发布包；超范围变更要求重新设计/批准，而非修改内存对象后自证一致。
- 完成一次 `T1 → author → validate → TP → 已发布模板消费 → G1/G2 → render/check/review/G3` 的受控测试闭环；测试签名仅限合成环境，不能作为真实批准。

**退出：**回归证明“决定被执行”，受影响的两种几何消费者完成检查；首个实际渲染闭环不缺证据。工程测试完成与真实任务验收分别记录，渲染跳过不能标为全阶段完成。

**恢复：**仅环境失败且输入不变时沿现有 retry；设计、包或固定依赖变化时重新生成证据与相应审批。代码回退只回到兼容且满足当前安全基线的已验收版本，新格式不交由旧代码猜读。

### TM-2：证明适用范围和第二次使用（P0）

**目标：**把“样张能画”推进到“声明范围内的新任务能用”。

**任务**

1. 从 TM-0 证据提炼最少的输入前提、语义不变量、允许变化与拒绝条件，放在既有数据/表达/场景/布局/质量合同的正确所有者处，不复制一套自由规则引擎。
2. 创建验证与生成侧适用性检查消费相同声明。缺原始类别或指标依据时澄清，不能由模板替业务补答案。
3. 保留现有网格和表达案例，增加真正挑战承诺的案例；明确必测集合并绑定模板、输入、检查器及预期依据，发布时核对完整性。
4. 优先复用 `template-validation-evidence.results` 等已有结构。需要新字段时明确演进 Schema；不能任意塞入无约束 `details` 或直接添加顶层 `stress` 来回避协议设计。
5. 对一个未参与作者调试的获准任务执行真实复用并独立审图；原始数据留在受控项目，包内只放安全验证材料。

**范围：**`C/workflow/template_validation.py`、现有场景 `validation_data_checker/validation_scene`、`C/validation/` 和生成侧相关检查；按必要性演进 `S/template-validation-evidence.schema.json`、相应业务合同及 `P/` 检查器声明。真实来源摘要优先复用已有受控准备链，未知来源类型仍拒绝，不伪装成 CSV。

**必须区分的四类结果**

| 输入 | 正确结果 | 核心证据 |
|---|---|---|
| 普通合法输入 | 成功 | 数据、表达、图例及批准设计一致 |
| 接近声明上限但合法的类别数/长标签 | 成功，或按已声明规则处理 | 真实字体度量、完整图例、实际尺寸成品；上限有依据 |
| 超界或语义不兼容 | 拒绝 | 明确到规则和字段的诊断，不删内容、不默改分类 |
| 缺少必要语义证据 | 澄清/未就绪 | 缺口、来源与受影响决定，不能记录为已验证 |

变形测试只用于有依据的不变量。例如无顺序语义的记录重排可保持制图语义，但行程顺序不可套用；源字节改变应使来源摘要改变，不要求不同来源的整包字节相同。

**退出：**普通和合法边界案例成功，负例正确拒绝，缺证据正确澄清；必测集合不能被删减；一个真实留出任务及独立业务/视觉审查完成。有限样本只支持声明的有限范围。

**失败处理：**收缩适用声明、修合同/实现或补原始材料；不默认新增 inset、重分类、OCR 或路线服务来消灭反例。扩大范围须作为明确的新决定。

### TM-3：提前补最小发现与生命周期治理（P1）

**目标：**用户能理解模板现在是否可用；错误版本能够停止使用，而不破坏历史。

#### 3A：只读发现与解释（可在 TM-0 后提前）

- 在唯一 CLI 内提供只读发现/检查能力，具体子命令在实现评审中确定；本计划不虚构已存在命令。
- 读取权威索引及经过校验的元数据，显示精确身份、历史发布事实、当前准入、适用前提、证据及不可用原因。
- 先实现列表与解释，再加入基于可信场景/几何/任务等信息的筛选。主题词相似不是适用性证明；信息不足返回待确认。
- 保持发现与安装/执行/审批分离。不得为列表操作自动创建项目、安装模板、发布、扫描未经授权的目录或输出业务数据。
- 回归包括“索引已发布但当前能力不准入”的版本，以及缺失、篡改或不可访问的元数据；明确未核验，不把历史 published 当成当前允许。

#### 3B：精确处置与影响查询（依赖合同和证据语义稳定）

1. 先定义状态/动作转移表，至少区分普通替代、停止新用和严重问题阻断；名称在协议评审时冻结，不把表达目录 FutureWarning 当成治理完成。
2. 保留包和发布历史不可变，在仓库侧形成受控处置记录；明确精确资产、原因、生效条件、作用域、责任人、授权、修订号与替代建议。具体是否新增 Schema 由现有协议能否安全承载决定，不承诺零协议改动。
3. 复用身份、签名、防重放和审计机制，但定义独立管理动作及对象。处置恢复/撤销也须授权并形成新记录，不删除旧记录。
4. 在新选用、安装和执行关键边界复核当前有效处置，正式交付提交前再次检查；应用缓存不得绕过有效版本/时效校验。元数据不可访问或有效性不明时，不能假定仍允许执行。
5. 受信回执证明既有运行身份与所用精确模板；仅修改 run_id 或时间字段不得伪装为“允许继续”的旧任务。
6. 在用户明确授权的项目根内，按资产及依赖摘要查询安装、候选、锁和交付引用；返回扫描范围、受影响项目和未知范围。第一版不建跨租户数据库或复制业务数据。

**涉及：**`C/repository/template_repository.py`、`template_installer.py`、`C/cli.py`、`C/scenario_registry.py`、生成与交付复核入口；`S/template-index.schema.json`、必要的处置/授权协议、`P/` 的相应规则与测试。

**行为与验收**

| 事件 | 新任务 | 已编译/已冻结未交付 | 已交付 |
|---|---|---|---|
| 普通新版发布 | 可显式选择新版 | 不自动换版，保持原引用并满足当前准入 | 保留原成果 |
| 停止旧版新用 | 阻止新用 | 仅在明确的既有运行处置及其他权限仍有效时继续 | 保留历史与说明 |
| 严重语义错误或授权失效 | 阻断受影响使用 | 已冻结不豁免；保留证据并阻断相关操作 | 形成影响报告及受控更正，不改写旧成品 |

**退出：**新/既有任务行为与转移表一致；已安装副本不能绕过；并发处置与执行、记录落盘/视图更新中断、重放和撤销均有测试；影响查询的未覆盖部分明确标未知。

**恢复：**处置与索引/视图采用可验证提交和恢复，不凭缺记录推定允许；恢复失败保持受影响动作关闭。普通代码回退不得撤销当前有效的安全阻断。

### TM-4：一个能力服务多个受控模板（P1）

**目标：**新增模板/版本不再要求复制场景实现，但仍不能凭声明获得新能力。

**任务**

1. 在既有注册表内区分业务/实现能力身份与模板资产身份。先限一个明确 namespace、现有业务与受信几何变体，不借机建设开放插件平台。
2. 能力声明可执行且获准的边界；模板声明所需能力及更窄的适用限制；发布证明精确资产满足要求；应用逐次核对需求、策略与当前处置。
3. 作者从已核准身份生成包，不再另外固定相同资产 ID/版本。未知实现、任意导入、超能力要求仍拒绝。
4. 用同一实现、两个有真实设计差异的模板资产验证；明确版本间语义差异与适用条件。仅修改版本号不是有效证明。
5. 复用 TM-3 影响查询，为主动换版给出受影响候选/锁与需重做的检查；不自动迁移或批量改引用。

**涉及：**`C/scenario_registry.py`、`C/scenarios/general_dispatch.py`、现有作者身份检查、`P/scenario-capabilities.yaml`、对应 Schema、仓库/安装/候选的引用消费与测试。不得仅删策略约束来开放模板。

**验收与退出**

- 同一受信实现支持两个经过验证的合法资产，无重复业务代码、固定身份分支或旧格式兼容旁路。
- 模板试图扩大业务用途、表达、后端或生产能力时被拒绝；模板与能力不匹配时发布和应用均拒绝。
- 同版本内容不可覆盖；新版不改变旧包、旧锁或已交付成果；正常替代和安全阻断的行为继续成立。
- 协议协调切换覆盖所有消费者；旧运行可审计，但若不兼容或不再获准则不得静默续跑。

**恢复：**资产保持不可变，通过受控准入/处置停止问题版本；必要时回到兼容且仍获准的已验收组合，不回滚审计历史或自动复用审批。

### TM-5：三场景逐项真实验收与经验回流（条件性接入）

**目标：**证明共用机制能服务明确业务，而不是仅增加三个场景名字。此阶段不是一个等全部基础设施完成才开始的大包。

| 场景批次 | 启动证据 | 最小技术与业务链 | 不得替代的验收 |
|---|---|---|---|
| 标准专题 | 来源、类别尺度、缺失值与用途已确认；TM-2 可承接首个验收 | 已有分类输入、模板创建/复用、图例/掩膜/表达检查、获准输出 | 正常、边界与第二份材料；不能把混合 NoData 的临时处置推广成普遍规则 |
| 政务专题 | 真实任务书、指标/单位/分母、时间、区划版本和比较要求 | 复用专题内核，补必要业务语义与审校约束；显式登记该用途 | 数量/比率混用、不同口径比较、区划变化反例；已有 general 指标图不算该场景验收 |
| 领导调研 | 获准地点/顺序/路线性质及敏感披露要求 | 来源准入、创建验证、数据准备、规划、候选、专业检查和交付；可先消费用户已确认的地点/路线，不强制新建服务 | 歧义地点、顺序变化、实际/示意路线混淆、敏感信息反例；T1→TP 的合成包不算真实任务闭环 |

共用完整执行链：模板侧 T1→author→validate→TP；地图侧 intake→brief/G1→compile→preview/G2→freeze→render→check→review→G3/deliver。精确操作顺序、对象和命令以届时已验收工作流/CLI 为准，不直接执行本文箭头。

新增场景除创建侧三个组件外，还必须有 `source_contract`，并完成 `data_preparer/planner/candidate_compiler/legend_checker` 等生成侧职责；以 `scenario_registry.py` 和场景组件协议核验，不以“已增加 profile”算完成。

**经验回流规则：**每次失败先归为数据、模板规则、实现或任务不适用。只有跨任务稳定出现、证据充分的规则才形成模板修订提案，经 T1/验证/TP 发布新版本；一次性实例问题不自动创建模板。

**退出：**每个场景分别形成完整真实证据包、独立审查、适用范围、已知限制和生产准入决定；不要求一起启用，不以总测试数或其他场景的批准替代。

**失败处理：**暂停该场景的相关操作或收缩其声明范围，不默认阻塞其他已独立验收能力；若暴露共用内核缺陷，按 TM-3 定位并处置全部受影响资产和运行。

## 五、每阶段统一的验收与版本规则

### 5.1 六项交付材料

每阶段都必须提交下列六项，复用既有开发记录和受控项目证据目录，不新建运行时读取的文档协议：

1. 实际范围、原始依据与非目标；
2. 改动文件、协议/模板版本、生产者与消费者清单；
3. 合法、非法、边界、缺证据与故障恢复用例；
4. 实际测试环境、命令、结果、跳过项和原因；
5. 该阶段所需的代表性运行/真实材料及独立审查证据；不适用项说明原因；
6. 已知问题、退出判定、恢复/回退方式及下一阶段条件。

责任分工：技术负责人对合同与全链消费者负责；业务确认人对语义及任务要求负责；测试/制图审查对独立预期与可读性负责；发布、管理处置与生产准入由对应受信审批主体决定。可以由现有团队承担，不要求新增服务或多智能体。

### 5.2 变化与失效

| 变化 | 必需处理 |
|---|---|
| T1 前来源或设计变化 | 更新分析与简报；重新确定批准对象 |
| T1 后设计/可调范围/模板依赖变化 | 新简报/运行和相应 T1，重新 author/validate/TP；不手改旧暂存包 |
| 仅验证环境故障，冻结输入不变 | 按现有 retry 保留旧尝试；不伪造渲染证据 |
| 包、必测集合、检查器或绑定环境变化 | 原证据不可直接沿用；按协议重验并重新批准发布对象 |
| 合法项目参数变化 | 走既有地图设计修订与相应审批，不发布无意义的新模板 |
| 冻结后设计变化 | 新运行/新锁，保留旧证据，不改写已冻结对象 |
| 普通替代或严重问题处置 | 依 TM-3 的授权和阶段规则执行；历史保留不等于继续执行许可 |

### 5.3 验收不能混淆

- 合成签名只证明测试链，不证明真实批准；HMAC、摘要和 schema 合法不证明业务正确。
- 真实材料运行、独立业务审查、实际尺寸视觉检查与生产准入分别记录。
- 边界测试的通过包含合法输入成功、非法输入拒绝和未知项澄清，不是全部拒绝。
- 关键计算预期来自手工小样本、原始定义或独立参考；不全部调用被测实现生成答案。
- 不因某个图面不理想就添加通用审美阈值；阈值必须来自已确认要求、标准或测量。

## 六、首个开工批次、暂缓项与停止扩展条件

### 6.1 首个批次只做 TM-0 和 TM-1 的最小闭环

- [ ] 列出当前准入/协议/消费者与本次工作区基线，确认可用解释器和测试环境。
- [ ] 将设计决定未消费的历史对照固化为回归，明确现有记录字段的语义。
- [ ] 选定一个受支持的设计维度，完成其字段、所有权、T1 对象与版本切换评审。
- [ ] 同批修改生产者、作者和应用消费者，使该设计维度全链生效，补未知/缺项/越权拒绝。
- [ ] 确认主样本与留出材料的授权和语义，冻结必需检查；不把观察过的所有材料都称作留出样本。
- [ ] 完成代表性渲染与适用阶段的真实验收记录，再决定后续参数和场景范围。

“一个设计维度”用于尽早验证因果链，不是只修一个字号常量就宣称 TM-1 完成。阶段完成还需覆盖本批明确承诺的全部字段和受影响消费者。

### 6.2 当前暂缓

独立 Brand/Style/Layout 全功能作者、任意 GIS/图片逆向、自动目录注册算法、复杂推荐、企业库、全项目自动迁移、自由布局平台和无依据的跨场景扩张。无模板项目内设计仅在现有“基础模板＋获准实例调整”迫使用户制造无意义模板时重新提高优先级。

### 6.3 停止扩展的条件

对一个已明确任务族，满足下列条件即可停止增加功能、转入维护：

- 用户主要提交本次数据与变化，不重复描述全部稳定规则；
- 新任务在范围内能复用，范围外能正确拒绝或澄清；
- 批准规则、有效设计和最终成果一致且可追溯；
- 新版本不悄悄改变旧项目，问题版本可停止使用并定位影响；
- 留出材料、独立业务审查与实际输出检查完成；
- 相同任务基线对照表明重复配置/返工减少，且未增加误用。缺基线时先测量，不填写虚构收益数字。

**实施顺序的核心：先把规则用对，再证明能复用；发现与治理及时跟进，业务范围由真实证据逐项扩大。**
