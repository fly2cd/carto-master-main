## 一、总裁决

本次确认采用以下原则：

1. **保留现有五类来源主体**：`platform`、`map-scenario`、`map-style`、`map-layout`、`project`。
2. **不把这五类主体当成完整的领域模型**。它们主要说明规范或配置来自哪里，不能单独说明每项决定的语义归属。
3. **补足表达／内容组件定义的合同权威**，但本轮不据此新增一批模板种类或并列 owner。
4. **Scenario、Style、Layout、Project 不合并**。它们的生命周期和变化理由不同。
5. **页面布局与组件内部排版分界**；注记也不能全部归给页面 Layout。
6. **每项实例决定只有一条有效来源链**，但可以同时受到多个不同性质的约束。
7. **程序负责验证和机械推导，不成为未声明设计决定的来源。**

现有代码的 `OwnershipResolver` 主要处理整段来源和替换；本裁决补充的是它之上的**语义权威与合同职责模型**，不是立即重写该解析器。

## 二、统一四个概念，避免再混称“所有者”

| 概念 | 回答的问题 | 示例 |
|---|---|---|
| **规范权威** | 谁定义这个决定的含义、合法参数和约束？ | Style 定义文字外观；Layout 定义页面容器；组件定义规定卡片接受什么内容 |
| **配置来源** | 本次配置来自哪里？ | Scenario 内嵌预设、独立 Style、独立 Layout、项目参数 |
| **实例选择** | 本次任务明确采用什么？ | 项目选择某个 Style，并将标题字号设为公开范围内的值 |
| **机械推导** | 根据已确定输入，程序算出什么？ | 字体测量、换行、高度、坐标换算、图形实例 |

### 裁决 1：字段所在文件，不自动决定语义所有权

例如：

- Style 内嵌在 Scenario 包里，字号仍属于外观决定；
- Layout 的内边距被复制到解析后的 appearance 对象中，来源权威仍是 Layout；
- 颜色进入图形实例后，Renderer 不因此获得重新选色的权利。

因此，必须同时记录：

> **语义由谁定义，值由哪里提供，本次如何采用，最终如何推导。**

### 裁决 2：多约束不等于多重权威

例如：

```text
Style：允许的字号与默认字号
项目：明确选择本次字号
Layout：提供实际容器空间
场景／标准：提出必须满足的可读性要求
```

这些约束可以共同作用，但不能各自保存一份可独立修改的“最终字号”。

若它们无法同时满足，应报告冲突。只有明确采用了合法适配策略，程序才可以计算适配结果。

## 三、现有所有者是否足够？

### 3.1 保留的边界

| 来源主体 | 应保留的职责 | 不应扩张到的职责 |
|---|---|---|
| **Platform** | 安全、协议、能力准入、标准引用、受信执行与验证机制 | 隐式选择风格、布局、颜色或业务内容 |
| **Scenario** | 可复用业务语义、必需内容、用途限制、允许的表达条件、默认方案 | 垄断全部视觉配置，或把模板身份等同业务能力 |
| **Project** | 本次数据绑定、内容选择、设计组合、允许范围内的参数选择 | 改写业务事实、越过硬约束、修改已发布合同 |
| **Style** | 外观常量、文字层级、符号外观、明确的注记视觉规范 | 数据字段含义、显示哪些业务信息、页面容器坐标 |
| **Layout** | 页面结构、容器、内容接口、视图关系、页面级布局与容量约束 | 重新解释业务数据，或接管所有组件内部结构 |

### 3.2 不新增的并列所有者

本轮**不直接新增**：

- `map-content`；
- `map-annotation`；
- `map-card`；
- `map-basemap`；
- “协议治理”模板。

原因是这些名称目前更多代表职责或组件，不一定需要独立的创作、检索、发布与治理生命周期。为了容纳几个字段就增加模板类型，会扩大模型而不一定增加清晰度。

### 3.3 必须显式化的合同权威

**表达／内容组件定义必须获得明确的合同地位。**

它负责定义：

- 输入类型与语义条件；
- 内容接口；
- 参数含义、单位及作用域；
- 内部结构或已登记的结构模式；
- 测量和图形生成规则；
- 所需后端能力；
- 哪些参数由 Style、Layout 或项目绑定提供。

已有表达目录可以承载其适合的部分。卡片等复合内容应通过受信组件协议扩展，**不预设所有内容组件都必须伪装成一个地理图层表达**，也不在本裁决另立第二套组件运行体系。

**结论：五类来源主体暂时保留；需要补足合同权威，而不是立即增加机器 owner 枚举。**

## 四、各决定域的合同边界

下表是确认采用的语义裁决，不代表新增八种模板。

| 决定域 | 规范权威与合同职责 | 实例选择及机械执行 |
|---|---|---|
| **业务语义与必要内容** | Scenario 定义角色含义、必需信息、业务不变量和用途限制 | Project 绑定本次事实；程序检查一致性，不推断或改写事实 |
| **本次显示内容** | 场景允许／必需内容约束，加类型化内容接口 | Project 选择显示哪些合法信息；程序格式化和生成内容实例 |
| **表达方法与组件结构** | 已登记表达／内容组件定义 | Project 选择方法或结构模式；程序验证并执行 |
| **视觉外观** | Style 的角色规则、外观参数与公开调整接口 | Project 选择 Style 和合法参数；程序解析有效外观 |
| **页面构成** | Layout 的画布、容器、内容接口、视图关联与容量约束 | Project 完成内容绑定和布局参数选择；程序推导页面几何 |
| **组件内部排版** | 组件定义的结构、测量规则及显式参数接口 | Project 采用结构模式和参数；程序结合字体与可用空间测量 |
| **地理视图与底图显示** | 数据／空间／视图合同，区分测量事实与显示策略 | Project 选择获准视图参数；程序执行配准、窗口测量和变换 |
| **安全、协议和执行能力** | 平台策略、注册表、适用标准及严格协议 | 程序具有验证权，但不能据此补做创意设计 |

### 默认值的统一规则

默认值不是例外通道：

- 可以由经过版本化的合同或预设提供；
- 可以在公开接口允许时被项目显式实例化；
- 必须能够追踪到唯一有效来源；
- 不允许 Renderer 或辅助函数另有一套未声明的设计默认值。

组件定义中的默认结构可以复用，但必须是**登记过、被采用的设计内容**，不能仅仅因为某段代码一直这么画，就认定它具有规范权威。

## 五、争议边界的具体裁决

### 5.1 页面 Layout 与卡片内部排版

**裁决：外部空间与内部结构分开。**

页面 Layout 决定：

- 卡片位于地图内、侧栏或其他容器；
- 可用空间和外部间距；
- 卡片集合与地图、标题、图例的空间关系。

卡片组件定义决定：

- 接受哪些类型的内容；
- 标题区、正文区等内部结构；
- 内部排版参数的含义；
- 怎样测量和报告溢出。

Style 决定：

- 文字和背景外观；
- 文字层级；
- 边框、引线等视觉属性。

#### 允许两种组织方式，但不能同时成为权威

1. **原子组件方式**  
   Layout 给卡片一个容器，组件负责内部排版。

2. **显式子内容方式**  
   设计者确实需要独立控制标题、正文等区域时，由明确的布局结构组织这些子内容。

第二种方式下，不能又保留一套可独立修改的“整张卡片内部布局”。同一内容也不能既由整卡渲染，又作为子内容重复渲染。

这延续了现有“Frame 承载组件，不接管组件内部”的方向，但允许真正需要独立布局的内容被显式拆开。

### 5.2 注记的边界

“注记”不是一个不可再分的所有者。

| 决定 | 归属 |
|---|---|
| 哪些地点必须有注记，哪些信息不可丢弃 | Scenario／项目内容计划 |
| 不同注记角色采用什么视觉层级 | Style |
| 优先级、重叠许可等已定义的显示规范 | 明确的注记规范；可由 Style 提供，但不得放宽场景硬约束 |
| 本次采用什么放置模式、哪些位置固定 | Project 的注记布局选择 |
| 可用地图范围、容器和障碍边界 | Layout／视图合同及已解析图形 |
| 具体避让位置 | 受信算法的机械结果 |

**禁止：**

- 以“低优先级”为由删除场景要求必须显示的内容；
- 求解失败后自动缩字或删标签；
- 为了好看而改变地理锚点；
- 把算法选择的坐标反过来当成新的业务事实。

### 5.3 底图处理的边界

必须分清：

1. **来源事实**：图片字节、原始尺寸、CRS、配准参数；
2. **显示策略**：是否裁边、采用哪个窗口、如何取景；
3. **布局安排**：视图放进哪个容器；
4. **机械结果**：变换矩阵、实际窗口和页面坐标。

背景判定阈值、裁边等不能因为现有字段恰好放在样式对象里，就继续被当作换肤参数。

### 5.4 符号度量的边界

符号可以采用不同度量模式，例如物理单位或参考设计像素，但模式及规则必须明确。

当前的参考尺寸、缩放下限属于**特定度量规则**，不是所有地图必然遵守的数学真理。

裁决为：

- 度量含义与可用模式由表达／符号定义说明；
- 本次使用哪种合法模式由设计选择确定；
- Style 提供相应单位下的外观参数；
- 程序执行明确的换算；
- 不将某个历史参考画布默认为所有模板的通用设计依据。

## 六、案例检验一：上午／下午路线

### 6.1 合法决定链

| 环节 | 决定 |
|---|---|
| Scenario | 定义行程分组、访问顺序等业务含义 |
| 数据证据 | 确定哪些停靠点和路线属于哪个分组 |
| Project | 明确采用按时段区分的表达，绑定分组与视觉角色 |
| 表达定义 | 说明分类路线、方向箭头、显示偏移的输入和参数语义 |
| Style | 为已绑定视觉角色提供颜色、线宽等外观 |
| Layout／视图 | 提供地图容器及展示范围 |
| 程序 | 生成有效路线图形和由同一映射派生的图例 |

### 6.2 预期不变量

- 换 Style，不改变上午／下午的成员关系；
- 换 Layout，不改变路线事实和访问顺序；
- 图例文字与实际分组语义一致；
- 图例颜色来自实际采用的视觉映射，而不是另一张手工颜色表；
- 显示偏移不写回原始路线。

### 6.3 应拒绝或澄清的情况

- 数据分组缺失，Style 擅自把它归到“下午”；
- Style 自带标签把上午改成“重点路线”，但项目没有改变表达含义；
- 路线用一种颜色，图例使用另一套独立映射；
- 箭头表达不受当前后端支持，却因 Schema 合法而继续执行。

**检验结论：**不需要新增“行程分组样式所有者”。业务含义、映射选择、外观和执行定义分开即可。

## 七、案例检验二：到达时间卡片

### 7.1 合法决定链

| 环节 | 决定 |
|---|---|
| 场景数据合同 | 到达时间的含义、类型及缺失处理要求 |
| 数据证据 | 本次真实值是什么 |
| Scenario | 该信息是否必需、是否允许隐藏 |
| Project 内容计划 | 在约束内选择本次显示内容及显示格式 |
| 卡片组件定义 | 接受标题、时间、说明等内容，定义内部结构和测量接口 |
| Style | 提供标题、正文等文字角色的外观 |
| Layout | 提供卡片容器或卡片集合所在区域 |
| 程序 | 测量、换行、计算高度及最终位置 |

### 7.2 图内卡片改为侧栏卡片

允许变化：

- 外部位置和可用空间；
- 根据明确规则重新计算的换行和高度；
- 合法的内容集合组织方式。

不应隐式变化：

- 到达时间的值；
- 是否显示必需信息；
- 地点身份与关联关系；
- 已采用的字体角色和颜色。

### 7.3 容量冲突如何处理？

假设内容和所选字号放不进容器：

- Layout 不能自行删除到达时间；
- Style 不能自行改写文字内容；
- 组件不能无声明地缩小字体；
- Renderer 不能截掉正文后仍报告成功。

可以执行的行为只有：

- 已明确允许、满足边界的适配；
- 报告冲突，返回设计修订。

### 7.4 应拒绝的情况

- 卡片组件和 Layout 各保存一份不同的内部标题坐标；
- 同一内容同时由整卡和子内容绘制；
- 数据缺失时为了完整展示而编造到达时间；
- 换 Style 后，时间字段被旧私有开关悄悄隐藏。

**检验结论：**需要明确的卡片组件合同，但不因此必须新增 `map-card` 模板种类；也不能把所有内部排版塞进页面 Layout。

## 八、案例检验三：底图裁边与符号缩放

### 8.1 两条转换链必须分开

**地理锚点与图像放置：**

```text
地理坐标与配准事实
→ 原图坐标
→ 显示窗口坐标
→ 视图容器
→ 页面坐标
```

**符号外观与度量：**

```text
已声明的符号度量模式
＋ Style 中的尺寸
＋ 必要的参考规则
→ 有效符号尺寸
→ 后端绘制单位
```

两条链最后在绘制时结合，但不能混用缩放因素。

### 8.2 权威划分

| 决定 | 权威 |
|---|---|
| 原图尺寸、原始配准与地理位置 | 数据／空间来源及其证据 |
| 裁边方法、背景判定条件、取景选择 | 视图显示合同与项目选择 |
| 地图容器大小与位置 | Layout |
| 符号采用物理单位还是参考设计单位 | 表达／符号度量定义与本次选择 |
| 具体颜色、线宽、字号 | Style |
| 实际窗口、变换、像素尺寸 | 程序机械推导 |

### 8.3 预期不变量

- 换路线颜色，不改变裁边窗口；
- 换页面容器，不改原始配准事实；
- 裁边后仍能正确映射原有地理锚点；
- 物理单位模式下，改变 DPI 不应改变声明的物理尺寸；
- 参考设计单位模式下，按已声明规则变化，不能套用“所有模式都必须物理尺寸不变”的错误验收标准；
- 相同缩放不得在组件编译和后端绘制中重复应用。

### 8.4 应拒绝的情况

- 图片已经缩放，却继续使用原图配准参数而不声明变换；
- 裁边窗口变化未进入证据与相关解析结果；
- 为适配页面擅自改变路线或停靠点坐标；
- 后端根据自己的默认参考画布重新计算符号尺寸。

**检验结论：**底图显示处理与符号度量应有独立、明确的合同职责，但不需要因此立即新增一种底图模板所有者。

## 九、合同随场景变化的裁决

本次确认以下规则：

1. **数据或设计实例不同**：改变值、角色条目、绑定和公开参数，不自动修改通用 Schema。
2. **新增业务语义**：优先扩展场景合同和内容绑定，不向通用 Style 不断增加业务开关。
3. **新增表达或内容组件机制**：扩展受信组件定义、参数 Schema、消费者和测试。
4. **新增通用布局或空间机制**：按协议演进处理，不能只增加字段而没有执行能力。
5. **不能容纳的字段应拒绝或进入正式扩展流程**，不提供任意键值扩展袋。
6. **同一含义只保留一处可修改的作者来源**；解析结果可以复制数值，但必须是可追溯、不可独立改写的派生副本。

## 十、已确认的裁决项与后续边界

以下 D1–D7 已由用户确认，后续字段映射应以此为设计依据：

- **D1**：保留五类来源主体，不直接把它们当作全部语义权威。
- **D2**：不合并 Scenario、Project、Style 和 Layout。
- **D3**：显式补足表达／内容组件定义的合同地位，暂不新增并列模板种类。
- **D4**：页面容器与组件内部结构分开；原子组件和显式子内容两种组织方式不能形成双重权威。
