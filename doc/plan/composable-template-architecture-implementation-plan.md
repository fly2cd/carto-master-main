## 1. 决策摘要

### 1.1 核心判断

当前通用专题制图已经具备较实质的组件化基础，但“通用专题业务”不等于“通用组合内核”。实施应当：

1. 修复段引用在现有生成入口中的接线缺口。
2. 提取通用专题中真正通用的合同解析、角色绑定、外观解析、版式编译和冻结能力。
3. 分步解耦业务能力与模板身份：首期建立能力上下文与组合适用性校验，保留已登记 Scenario 身份准入；完全解除固定 Scenario 身份分派作为后续 P3b 单独评审。
4. 允许一次地图任务独立选择 Scenario、Style、Layout，并形成项目级组合实例。
5. 把已有检索、需求判断、草稿生命周期连接到现有生成链。
6. 用通用专题和领导调研两个独立场景证明可组合性，而不是把后者伪装成前者。

### 1.2 不采用的路线

- 不把 `general_thematic_mapping` 扩展成所有业务的总场景。
- 不把领导调研的 `image_itinerary` 私有样式合同原样升级为通用标准。
- 不通过放宽模板白名单、关闭摘要检查或绕过审批制造“任意组合”。
- 不使用任意深层 merge 或“后加载覆盖前加载”解释组件所有权。
- 不新建独立的地图生成状态机、模板发布系统或冻结对象权威。
- 不要求每种组合先发布成一个新的完整 Scenario 包。
- 不把 Schema 合法、存在检索命令、单模板验证成功当作组合端到端可用。

### 1.3 交付分层与本期承诺边界

以下区分完整目标与获准后才执行的交付批次；“首期承诺范围”指本计划建议的实施包，不表示用户已经批准实施。

| 交付层 | 含义 | 对应阶段 | 承诺状态 |
|---|---|---|---|
| L0：基线可靠 | 修复现有段引用单候选入口回归，并防止合并再次回退 | P0 | 独立紧急修复包，可单独授权，不等待整份架构计划批准 |
| L1：有界项目级组合 | 在已登记 Scenario 与能力范围内，独立选择已发布 Style/Layout，校验、冻结并生成 | P1、P2、P3a、P4 | 建议首期核心范围；P0–P4 不含 P3b 完全身份解耦 |
| L1+：扩大 Scenario 身份适配 | 同一业务支持更多合法 Scenario 身份，不再以固定模板身份作为唯一分派依据 | P3b | 以 P4 和摘要影响证据为门槛，单独承诺 |
| L2：跨场景组合闭环 | 检索接入生成，通用专题与领导调研均通过共享接口使用组件 | P5、P6、P7 | P4 验收后再评审承诺，不与首期捆绑 |
| L3：草稿直接消费 | 未发布但已验证的项目段草稿进入正式地图链，不暗中发布 | GD | 单独评审与验收，不阻塞 L1/L2 |

首期不承诺自动检索到生成、多组合比较预览、领导调研完整迁移、任意 Scenario 身份准入或草稿直接正式制图。L2 是总体方向，不再作为一次性必须兑现的首期交付。

收窄范围不削弱安全和质量要求：P4 自身必须完成共享变更所需全量回归、漂移/恢复/审批检查和真实渲染，不能等待后续 P7 再补。未完成 P3b 时不能宣称“能力与模板身份已完全解耦”；未完成 GD 时明确草稿不能直接正式生成。

## 4. 目标架构与职责

### 4.1 目标调用链

```text
用户目标 + 已确认业务要求 + 已获准数据概要 + 输出约束
                         ↓
             场景语义 / 类型化设计需求
                         ↓
       已有模板检索、硬条件核验与候选解释
                         ↓
          LLM/用户显式选择组件及设计参数
                         ↓
      版本化生成请求：项目级组合选择与数据绑定
                         ↓
          intake → brief → [G1] compile
                         ↓
     精确组件解析 → 所有权核验 → 联合编译与检查
                         ↓
       MapPlan / resolved-* / RenderScene
                         ↓
     preview → 选择最终候选 → [G2] freeze
                         ↓
       render → check → review → [G3] deliver
```

已发布模板可直接复用；参数化不产生新包。派生/创建进入已有段草稿工作流，是否发布由显式发布请求和 TP 决定。GD 未准入时，草稿停在设计/验证产物，不绕过来源准入。

### 4.2 单一职责表

| 层次 | 拥有的决定 | 禁止接管的决定 |
|---|---|---|
| 场景插件 | 业务任务、数据语义、必需内容、允许的表达语义、来源准入 | 复写通用布局坐标或通用绘图机制 |
| 表达目录与受信实现 | 输入语义、视觉映射条件、计算与图形机制 | 推断用户业务意图或授予执行权限 |
| Style | 稳定视觉角色的外观、字体层级、符号配置、公开参数 | 业务数据行、地理事实、页面坐标 |
| Layout | 画布、容器、空间关系、容量和声明式适配 | 数据字段推断、删减必需业务内容 |
| 组合解析器 | 精确来源、唯一所有权、引用闭合、参数校验和来源追踪 | 根据相似分数自行决定最终风格或版式 |
| 共享编译层 | 角色/插槽绑定、测量、确定性推导、页面实例与场景生成 | 读取领导调研或其他业务私有词汇 |
| 渲染后端 | 按冻结实例绘制、导出及生成执行证据 | 重新选模板、改色、变换版式或静默替换字体 |

### 4.3 依赖方向

```text
workflow / 受信装配入口
  ├─ 注册表 → 场景端口（业务语义）
  ├─ 组件解析端口 → 仓库或获准项目草稿解析器
  ├─ 共享组合/页面编译端口
  └─ 已注册后端

具体场景 → 共享叶子协议与编译服务
共享内核 -X→ import 具体场景模块 / 直读具体场景请求词汇
```

复用抽象优先使用现有 `contracts/protocols.py`、`compiler/component_protocols.py`、组件清单和装配入口。只有发现明确缺失的职责才新增模块，且仍位于唯一实现根内。

## 5. P1 必须冻结的协议决定

### 5.1 项目级组合选择

演进现有生成请求与 MapPlan，增加闭合的“组件选择”结构，而不是新建另一套执行计划。正式字段名与版本号在 P1 的生产者—消费者清单中确定；下列名称仅表达目标含义，不是可直接提交的现行请求：

```text
本次组合选择
  scenario：精确业务方案引用
  style：精确段引用，或由明确选定的 Scenario 基线提供
  layout：精确段引用，或由明确选定的 Scenario 基线提供
  parameters：各组件公开参数的显式取值
  bindings：数据角色 → 表达角色 → 内容/视图 → Layout 插槽
  provenance：需求、选择、基线与覆盖来源
```

规则：

1. 每个段只有一个有效来源；基线、替换、实例参数不能重复拥有同一决定。
2. 沿用既有 `style` / `layout` 段命名和语义；不增加 `cartography` 等别名作为第二入口。
3. 引用必须明确 namespace、kind、id、version、digest 及受信库作用域；跨库解析不按名称猜测。
4. `embedded` 与段引用的所有权约束继续有效；运行时替换只能作用于明确允许的段。
5. 参数必须由组件声明，包含类型、单位、范围及作用域；未知参数拒绝。
6. 硬约束共同满足；默认值可以显式实例化，不能被无限制补丁覆盖。
7. 依赖闭包、资源、有效合同和参数进入执行摘要；检索分数和解释不成为渲染决定。
8. 默认方案是显式可选预设，不是通用内核硬编码。默认展开必须在冻结请求前完成，并由内核复验；不得修改已 intake 的请求来补引用。

### 5.2 业务准入与模板身份分离（完整目标；首期窄增量见 §10）

- 先根据业务场景、任务、显式几何及受信能力上下文确定唯一能力档案；存在歧义则澄清。
- 再核验所选 Scenario 的语义、表达要求、组件需求、后端及输出是否满足该档案。
- 模板包身份仍用于完整性、版本、发布与追溯，但不再是业务实现的唯一分派键。
- 代码实现与后端仍使用受信注册表白名单，模板不能携带任意 Python 导入路径。
- 已发布/有 TP 只证明模板来源和发布流程，不自动证明对当前场景、数据、媒介可执行。
- 生成、模板创建、预览、冻结、正式渲染、终检、交付和恢复采用一致的准入判定，不能只改 intake。

### 5.3 三类绑定不能混为一谈

| 绑定 | 例子 | 权威 |
|---|---|---|
| 数据语义绑定 | 哪一列代表类别、哪个对象代表停靠点 | 场景与本次数据证据 |
| 表达/视觉角色绑定 | 类别采用何种符号、调研点采用编号点与卡片 | 本次表达选择及 Style 适用合同 |
| 页面内容绑定 | 地图、图例、卡片列表放到哪个容器 | 本次内容计划与 Layout |

Layout 不读业务字段；Style 不保存具体地名；程序不能把字段名近似、角色缺失或空集合视为匹配成功。

### 5.4 公共协议与策略变更纪律

- P0、P2 属于修复/纯重构：保持现有请求、提案、策略语义和业务产物形状；代码指纹变化按现行 doctrine 处理。
- P3a/P4 如增加公共协议必须明确版本化；P3b 的身份准入/策略语义扩展单独提交与评审。纯内部校验提取不得顺带改策略摘要，任何真实语义变化也不能假称为重构。
- `scenario-capabilities` 等语义策略变化必须由 `.github/CODEOWNERS` 中的唯一策略 steward 评审；当前配置为 `@liudakemgslab`，实施时重新核实。
- 新协议提供合法、非法样例和自动测试；未知字段默认拒绝，Schema 保持 Draft 2020-12。
- 不增加旧请求别名、旧锁兼容分支或自动迁移器；需要使用新协议的运行重新准备、审批、编译和冻结。

## 12. P5：检索与多组合候选接入

本阶段为 P4 证据通过后才承诺的续阶段。检索与创作相关文件由原模板创作/复用工作面主责，组合架构线通过接口需求和集成用例协作，不整文件覆盖既有成果。

### 12.1 复用与补齐

继续使用 `template match / resolve / orchestrate`、`design-requirement`、`design-resolution-result` 及已有创作生命周期，补齐：

1. **受信场景上下文**：取消 resolve 中固定 general 档案的逻辑，使用当前获准业务能力及输出约束。
2. **类型化事实适配**：Style、Layout、Scenario 分别提取能形式化验证的事实；Style 不能交给 `LayoutResolver`。
3. **联合候选检查**：在单组件条件通过后，对组件间角色、容量、字体、图例、后端及数据实例条件检查。
4. **搜索完整性**：记录来源范围、过滤条件、候选预算、参数域覆盖和截断情况；预算耗尽返回不完整，不直接判断“应新建”。
5. **选择权**：排序只提供建议；由 LLM/用户提出明确选择和参数。未知硬条件阻断精确复用。
6. **生成连接**：选中引用与参数进入正式请求，检索解释作为证据引用，不重新成为执行权威。

### 12.2 多候选的必要改造

- 每个候选有自己的完整组合、MapPlan、绑定、有效外观、布局及摘要。
- 数据证据仅在上下文和输入摘要相同且依赖判定允许时共享；不得把第一个候选的计划套给其他 Layout。
- 比较预览必须渲染真实候选，并记录每个候选的预检/渲染结果；失败项不可被选择冻结。
- 目标流程为 `compile候选集 → preview候选集 → select-candidate → freeze`。如与当前步骤顺序不同，版本化演进现有状态机，不另建候选状态机。
- 单候选继续走简化路径；候选数量、渲染次数及工具调用均使用既有累计预算机制。
- 最终选择不影响原始业务事实；只有选中且证据完备的候选进入精确 G2。

### 12.3 退出条件

结构化需求能够从库中得到有解释的候选、显式选择、联合编译和最终冻结；不符合条件或搜索不完整时不会默默套用默认模板。自动推荐不是执行授权，也不是业务确认。

| 地图、标题、图例、来源、卡片列表空间关系 | Layout + 显式内容插槽绑定 |
| 地理坐标到配准图片坐标转换 | 既有受信空间适配能力，保留授权与证据 |
| 本次分组、编号语义与卡片内容 | 场景/项目决定；程序不推断或删除业务内容 |

### 13.3 工作项

- [ ] 将私有合同中的配置逐项登记到通用角色与参数：消费点、单位、默认来源、约束、摘要绑定逐项可追踪。
- [ ] 参考像素、原图像素、页面像素、毫米和 pt 不混用；迁移样式值时显式声明换算规则并验证不同 DPI。
- [ ] 原 `image_itinerary` 不保留为第二套有效样式权威。涉及公共请求变化时发布新协议；旧产物不自动补齐或自动迁移。
- [ ] 取消 `main-map` 等字符串对所有 Layout 的隐式要求，改为已验证的视图/内容绑定。
- [ ] 对地点和路线分别绑定分组角色，避免请求骨架缺少 route-line 绑定导致默认配色。
- [ ] 标题/正文/图例字号及图框来源统一；任何 shrink、clip、分页或注记丢弃必须由合同允许，不能沿用无声明的隐式调整。
- [ ] 前端地图文档与 PDF/PNG 使用同一解析实例和共享几何推导；不以某一端重新设计弥补另一端缺字段。
- [ ] 调整作者、编译器、修订合同和必要的宿主请求骨架；不修改路线准备的数据事实和审批边界。

### 13.4 退出条件

- 至少一份满足共同接口的 Layout 可被通用专题和领导调研复用，且不新增共享内核中的场景名分支。
- 至少一份包含双方所需视觉角色的 Style 可跨场景使用；不声称所有 Style 天然跨场景兼容。
- 同一行程换 Style/兼容 Layout 后，地点、访问顺序和路线事实保持不变。
- 领导调研新增合法 Style/Layout 不再需要改其候选编译器。
- 通用专题、领导调研及前端/静态输出回归均有证据；真实敏感数据仍未因迁移而自动准入。

### 13.5 先行技术验证：单位与几何不变量

这是完整迁移的进入条件，不是末尾补一张截图。使用合成数据固定：源图尺寸、非零裁边窗口、配准矩阵、地图框、参考设计尺度、字体和 DPI。

| 坐标/度量域 | 必须明确的合同 |
|---|---|
| 地理坐标 / 工作投影 | CRS、轴顺序、单位及 pyproj/PROJ 版本；不改变原始路线事实 |
| 原图像素 | 像素中心、零基索引、原图尺寸与配准关系 |
| 显示窗口 | 裁边原点与宽高；不能把窗口坐标当原图坐标 |
| 参考设计像素 | 参考尺寸与现有缩放/下限规则，区分符号尺寸和坐标位置 |
| 页面像素 | contain 缩放、居中偏移、DPI/DPR 与页面框绑定 |
| mm / pt | 线宽、字体、边距等物理量的唯一转换点，不重复缩放 |

技术验证至少覆盖：非零裁边、不同图像长宽比、144/200/300 DPI 的合法子集、旋转/非轴对齐配准、路线经过停靠点、卡片锚点和前端/静态输出对应关系；不满足当前准入的组合作为明确反例，不借验证开放能力。

实施前固定几何容差、字体/边界测量方法、等价性定义和误差报告格式，禁止看到结果后放宽阈值。对比迁移前后的地理事实、原图锚点、物理线宽和字号，不能仅以图片视觉近似代替证明。

技术验证产物包括单位流向图、转换点清单、错误累积测量、当前合同不能无损表达的项目，以及完整迁移估算。若不满足不变量则修订接口或暂缓 P6，不保留私有合同与通用合同两个运行权威。

## 15. 审批、修订、摘要与冻结规则

### 15.1 权限与时序

1. 检索可使用已允许的模板元数据和用户声明；读取、统计真实业务数据仍需对应授权。
2. G1 前不能为了算卡片数或字段统计而私自预读未获准数据。
3. 初始组件选择、参数、资源及依赖摘要纳入请求和 Brief；需求只是建议时不得伪装为用户已确认。
4. G1 后发现实际容量不满足，应提出修订，走既有 `revision-brief → 新G1 → revise`，不得直接改冻结请求。
5. 组件或参数变化产生新候选与预览，新 G2 只批准对应精确对象；冻结后改变设计需新运行。
6. TP 只对应模板发布；不等于地图 G1/G2/G3，项目内组合本身不触发自动发布。
7. 成品 review、交付 Manifest 和 G3 保留；命令执行许可不等于业务审批。

### 15.2 失效与复用矩阵

| 变化 | 默认失效范围 | 数据证据复用条件 |
|---|---|---|
| 换 Style 或公开视觉参数 | 有效外观、相关表达图形、布局测量、候选、预览、G2 | 数据语义/处理输入未变，运行时摘要复验通过 |
| 换 Layout / 内容插槽 / 页面参数 | 计划绑定、布局、候选、预览、G2；地理取景受影响时同时失效 | 不隐式改变筛选、范围或数据准备 |
| 换表达方法或字段 | 表达计划、可能的数据处理、候选及后续全部 | 按依赖逐项证明，不默认复用 |
| 换 Scenario 方案 | 重新核验全部语义、来源与授权；首版按新运行处理 | 不推定复用资格 |
| 改数据文件、行程、路线 | 数据准备与受影响后续链 | 使用既有获准数据修订或新运行机制 |
| 改策略语义、表达定义、模板包或字体资源 | 所有受摘要影响的有效合同和冻结执行 | 漂移拒绝；重新准备/授权/编译/冻结 |
| 只改检索展示排序/说明 | 不得影响已显式选定的冻结执行 | 不改变任何语义选择或其证据声明；版本规则按协议界定 |

失效图必须由真实输入摘要门复核，不能仅靠静态规则宣称可复用。

### 15.3 冻结对象应能回答的问题

- 使用了哪个业务能力和哪些精确组件？
- 组件来自哪个作用域和仓库/项目草稿？
- 每个有效值来自基线、替换还是实例参数？
- 使用了什么字体、资源、表达定义、布局实例、后端与环境？
- 哪个数据证据、候选和预览被批准？
- 任何上述对象漂移时，由哪个门拒绝继续执行？

正式渲染只消费冻结对象，不重新检索、不获取“最新模板”、不按候选得分改选。

### 17.2 切换与回退

1. 切换前固定旧环境、模板库快照和运行清单；策略绑定变化前让可完成的旧运行先完成。
2. 未完成旧运行按现行 doctrine 在匹配环境继续，或以新版本重新准备/审批/编译/冻结；不改旧锁。
3. 新版以真实通过的组合范围开放；不因新 Schema 的枚举出现而开放全部组合。
4. 回退只能回退成套环境/策略与匹配产物，不把新锁交给旧代码，不原地重写旧模板。
5. 任何影响摘要的策略开关变更同样受治理，不使用临时 toggle 掩盖冻结漂移。

### 17.3 完成定义

P4 只能宣称“已登记 Scenario 范围内的项目级段组合已交付”。续阶段获准后，当且仅当以下条件同时成立，才能称为“跨场景通用组合闭环（已声明准入范围）已交付”；P3b 未完成时仍不得宣称任意 Scenario 身份准入：

- 两个独立业务场景通过相同组件接口使用可复用 Style/Layout。
- 新增兼容组件不需要修改具体场景代码或新增内核业务特判。
- 需求检索、显式选择、联合编译、真实预览、冻结和交付组成一个闭环。
- 语义、接口、物理或执行不兼容能够准确拒绝，并保留原因与来源。
- 正式执行不重新选择模板、不隐式调整设计、不复用不匹配审批。
- 未完成能力和环境跳过项明确列出，不以局部成功替代整体完成。
