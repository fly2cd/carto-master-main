## 第一部分：领导调研用图场景的模板应用逻辑

本部分沿着**请求构造 → 模板准入与安装 → 样式合并 → 场景编译 → 渲染与修订**梳理实现，并核对相关 Schema 和测试代码。

**核心结论：当前领导调研用图是“专用场景模板 + 本次请求的有限覆盖 + 行程数据绑定”的确定性编译流程。不是根据“领导调研”自动搜索一组风格、版式模板，再自由拼装。**

以下以讨论时读取的代码为准；部分工作流文档还保留着“仅支持 general”的旧描述。

### 1. 目前到底使用哪个模板？

当前策略将几种身份明确区分：

| 层次 | 当前值 | 作用 |
|---|---|---|
| 业务场景 | `leadership_visit` | 表示领导调研业务用途 |
| 业务任务 | `visit-route-map` | 表示行程路线图任务 |
| 能力档案 | `leadership-visit-mapping@1.0.0` | 声明该场景允许做什么 |
| 场景模板 | `map-scenario / leadership-visit-map@1.0.0` | 提供实际复用的合同 |
| 渲染后端 | `image-itinerary-page` | 在配准图片底图上绘制行程图形 |

来源：`skills/carto-agent/policies/scenario-capabilities.yaml:86`

这里有两层选择逻辑：

- **内核生成入口**：请求必须明确指定模板的 `namespace/kind/id/version`；注册表按模板身份查能力，并验证其与业务意图一致，不做模糊匹配。
- **MCP 请求骨架工具**：`request_scaffold` 会读取模板库索引，寻找固定 ID `leadership-visit-map` 的已发布条目，补上版本和摘要。这是固定模板查询，不是设计意义上的智能选模板。

对应代码：

- `skills/carto-agent/scripts/carto_core/scenario_registry.py:281`
- `services/itinerary-tools/request_scaffold.py:53`

**因此，普通生成请求不能任意换一个模板 ID 或版本，就期待系统自动适配。**当前准入策略绑定的是上述模板版本。

### 2. 模板从哪里来？里面装了什么？

领导调研模板由 `RouteAuthor` 生成。它目前是一个**专用、确定性的模板构造器**，主要内容来自代码中的常量：

- `TEMPLATE_STYLE`
- `LAYOUT_CONTRACT`
- `CARTOGRAPHY`

而不是每次由 LLM 临场设计一整套模板。

模板包的核心结构可以概括为：

```text
场景模板
├─ scenario
│  ├─ 业务场景、支持任务、适用范围
│  ├─ embedded.layout        页面与内容框
│  └─ embedded.style         通用制图风格合同
├─ data_schema               route-stops / route-line 数据角色
├─ spatial_behavior          坐标与路线顺序等约束
├─ portrayal
│  └─ image_itinerary        本场景实际使用的行程视觉样式
├─ delivery                  PDF / PNG 输出声明
└─ quality_gates             检查项
```

这里最关键的是：

> **行程点、路线、卡片的实际样式，主要来自 `portrayal.image_itinerary`，不是通用的 `embedded.style`。**

#### 默认版式

模板定义 A3 横版，`420 × 297 mm`，四个固定内容框：

| 内容 | `content_id` | 边界 `[x,y,w,h]`，单位 mm |
|---|---|---|
| 主地图 | `main-view` | `[20,30,380,230]` |
| 标题 | `title` | `[20,12,380,14]` |
| 图例 | `legend` | `[300,264,110,22]` |
| 来源说明 | `source` | `[20,264,200,22]` |

#### 默认行程样式

例如：

- 上午：蓝色 `#1769D2`；
- 下午：粉红色 `#E43D96`；
- 其他：紫色 `#403B96`；
- 路线宽度：参考值 `6px`；
- 地点标记半径：参考值 `12px`；
- 卡片宽度：参考值 `500px`，标题/正文为 `22px/14px`；
- 默认不显示到达时间；
- 卡片中的行程点编号按“日期＋分组”计数；
- 页面标题名义字号 `34pt`，来源说明 `12.76pt`，带双线图框。

代码：`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/route_author.py:36`

模板需要经过：

```text
analyze → brief → author → validate
→ prepare-publish → TP 审批 → publish
```

其中验证使用合成数据和真实渲染器。**模板发布一次后可以复用，不是每次生成地图都重新创建模板。**当前仍属于非生产准入。

### 3. “应用模板”具体发生在什么阶段？

主入口是：

`skills/carto-agent/scripts/carto_core/workflow/map_generation.py:172`

实际顺序如下：

```text
请求指定模板
    ↓
intake：验证业务意图、模板能力和请求结构
    ↓
brief：列出模板引用、数据计划、输出，绑定请求摘要
    ↓
G1 审批
    ↓
compile：
    ① 从已发布仓库安装精确模板
    ② 准备或复用行程数据
    ③ 读取并校验模板合同
    ④ 合并本次 style_overrides
    ⑤ 生成 MapPlan
    ⑥ 编译页面、路线、点、卡片、图例
    ↓
preview → G2 → freeze
    ↓
按冻结结果 render
```

#### 安装不是简单读取某个 YAML

`ProjectTemplateInstaller` 将模板复制到项目私有目录：

```text
.carto/templates/installed/
  local/map-scenario/leadership-visit-map/1.0.0/
```

安装和装载阶段会验证模板摘要、文件校验和、合同摘要、Schema、依赖锁等。已安装内容出现漂移会拒绝，不会静默采用改后的文件。

代码：`skills/carto-agent/scripts/carto_core/repository/template_installer.py:27`

所以：

- 修改 `route_author.py`，**不会自动更新已经发布或安装的模板**；
- 修改仓库中的参考资产，**也不会自动改变当前地图**；
- 当前地图实际依赖的是被引用、安装和校验过的模板包。

### 4. 模板和本次需求如何合并？

可以用下面的公式理解：

```text
本次有效行程样式
  = 已安装模板的 portrayal.image_itinerary
  + 请求中的 style_overrides 补丁
```

不提供补丁，就保持模板默认样式。

#### 合并规则并不是任意深度合并

`request_contract.py` 定义了明确规则：

| 字段 | 合并方式 |
|---|---|
| `groups` | 按已有 `id` 找到分组，只覆盖提供的属性 |
| `default_group` | 替换，但必须指向已声明分组 |
| `numbering`、`white_threshold` | 直接替换 |
| `route`、`pin`、`callout`、`support_label` | 分节按键覆盖 |
| `page_furniture` | 按键覆盖，其中 `frame_border` 再按键合并 |

**不能用补丁新增任意分组 ID。**例如默认模板没有 `evening`，补丁引用它会报 `LEADERSHIP_STYLE_GROUP_UNKNOWN`。

另外，`route.arrows` 是该节中的一个对象值，覆盖时要提供其完整合法结构，并非任意深层递归合并。

代码：`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/request_contract.py:29`

例如下面是一个请求片段：

```yaml
map_title: 调研行程路线图

style_overrides:
  groups:
    - id: morning
      color: "#228833"
  route:
    width_px: 8
  page_furniture:
    title_font_pt: 30
```

含义是：

- 修改本次地图标题；
- 将上午组改成绿色；
- 修改路线参考宽度；
- 修改页面标题名义字号；
- 其他模板配置保持不变；
- **不改写已发布模板包。**

标题还有独立优先级：

```text
request.map_title → request.goal → 内置兜底标题
```

因此这里不是简单将模板里的 `{{MAP_TITLE}}` 做文本替换，而是把标题作为页面内容，绑定到 `content_id=title` 的框中。

### 5. 模板配置怎样真正变成图？

具体实现位于：

`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/candidate_compiler.py:119`

#### ① 地理数据先映射到图片坐标

利用：

- 用户提供的底图图片；
- 配准参数；
- 已准备的行程点和路线；

通过工具网关完成地理坐标到原图像素的转换，再测量底图有效显示窗口。

**模板不会决定调研地点在哪里，也不会凭样式生成道路路线。**这些是数据准备的职责。

#### ② 版式决定底图在纸上的位置

`LayoutResolver` 把模板中的毫米框转换为页面像素框。

底图有效窗口通过 `contain_layout`：

- 保持宽高比；
- 缩放到主地图框内；
- 居中放置。

不是拉伸图片铺满整页。

#### ③ 样式结合数据语义生成图形

`apply_grouped_style()` 读取字段绑定，将数据中的分组、日期、地点名称、里程等转换成：

- 路线；
- 地点标记；
- 调研说明卡片；
- 起终点等辅助标签；
- 图例项。

这里有几个容易忽略的细节：

- 分组依赖 `itinerary-group` 的字段映射；缺少分组值或映射时使用 `default_group`，未知分组则拒绝。
- **路线和地点分别使用各自角色的字段绑定**，不会自动共享。
- `per-date-group` 控制的是卡片文字中的局部编号；点图形保留的 `visit_order` 仍是整体访问顺序。
- 路线、标记、卡片中的参考像素参数还会按底图有效窗口进行缩放，不应直接理解为最终 PNG 上固定不变的像素大小。
- 卡片先走确定性避让；请求还可以启用额外的注记布局求解。
- 页面标题字号是名义值，渲染时还会根据内容框容量限制实际字号。

代码：`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/style.py:75`

#### ④ 冻结图形，而不是渲染时重新套模板

最终生成：

- `page-request`：页面布局、标题、图例、底图等；
- `RenderScene.image_graphics`：已经计算好的路线、点、卡片；
- 候选执行描述及其模板、数据、环境引用。

PDF/PNG 渲染器和前端地图文档构造器共用这套冻结图形，避免两端各自解释模板、各自排版。

### 6. 当前实现有几处需要特别注意

#### A. 修改通用 `embedded.style`，不等于修改调研图的实际外观

模板确实带有 `CARTOGRAPHY`，但本场景的主要视觉消费者读取的是：

```text
portrayal.image_itinerary
```

页面标题等读取其 `page_furniture`；图例字号还有共享推导逻辑。

因此，**想改路线颜色、卡片字号，应走 `image_itinerary/style_overrides`，不能只改通用风格段就期待生效。**

#### B. `page_layout` 的声明能力大于实际消费范围

Schema 接受：

```text
model / width_mm / height_mm / dpi
```

但当前 `RoutePlanner`：

- 页面宽高仍取模板 `layout.canvas`；
- 从请求中读取 `dpi`；
- 将 `model` 写入计划。

候选编译器随后仍直接解析模板布局，没有根据 `model` 切换布局算法，也没有用请求的 `width_mm/height_mm` 重建版式。

**因此，当前仅改请求宽高，不能据此认为页面会从 A3 改成 A4；`image-native` 也没有形成独立的布局执行分支。**

代码：`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/planner.py:41`

#### C. 声明“可替换版式段”，不等于本场景已经打通段模板组合

领导调研模板声明了：

```yaml
replaceable_segments:
  - layout
```

但当前 `RouteAuthor.template_documents()` 仍直接内嵌固定布局，未消费请求里的 `segment_refs`。

此外，普通单候选生成路径调用 `load_contracts(installation)` 时没有传入段模板仓库，而装载器在遇到段引用时要求这个仓库参数。

所以，**不能把通用框架的段引用支持，直接理解为领导调研场景已经支持任意选择 `map-style/map-layout` 并组合应用。**

#### D. 请求骨架的默认绑定会影响路线是否按组着色

目前 `request_scaffold` 默认只生成 `route-stops` 的字段绑定，没有生成 `route-line` 的分组字段绑定。

而样式编译对路线读取的是 `route-line` 的 `itinerary-group` 映射。

**按这条默认请求路径静态推导：即使路线数据带有上午/下午信息，缺少对应字段绑定时，路线仍会落入默认组配色。**不能仅凭模板声明了上午蓝、下午粉，就断言所有路线都会这样画。

### 7. 已经出预览后，如何重新应用修改？

预览阶段的样式修改走：

```text
revision-brief
→ 新 G1
→ revise
→ 重新 compile
→ 重新 preview
→ 新 G2
```

样式变更一般可以复用行程数据证据，但候选、场景和预览需要重建。

还有一个细节：**修订中的 `style_overrides.new_value` 替换的是整个旧补丁对象，不是自动叠加到上一轮补丁上。**希望保留的旧覆盖项，需要继续包含在新补丁里。

代码：`skills/carto-agent/scripts/carto_core/scenarios/leadership_visit/revision.py:76`

---

**总结：当前模板化主要实现了“固定场景合同的发布复用、有限样式覆盖、数据驱动实例化和冻结重现”；还不是完整的通用模板检索、风格/版式自由组合系统。尤其要区分：模板中声明了什么、请求允许写什么，以及编译器最终真正消费了什么。**

## 第二部分：通用模板检索与风格／版式组合的目标架构

**我的判断是：合理，而且如果 Carto Master 的目标是“多场景制图平台”，这应当是核心架构能力，而不只是一个方便换皮的附加功能。**

但目标最好定义为：

> **从可复用模板库中检索候选，在业务语义、表达规则和输出约束下，组合风格与版式，形成可验证、可追溯的制图方案。**

不是“任意模板都能拼在一起”，也不是“让 LLM 随意覆盖所有配置”。

下面从目标合理性、必要性、架构和具体改动四个方面展开。以下是目标设计建议，不受当前固定模板实现方式限制。

### 一、为什么合理，是否有必要？

#### 1. 合理：业务、视觉与版式本来就不是同一个问题

以领导调研地图为例：

- 调研哪些地点、路线经过哪里，是**业务与数据问题**；
- 上午蓝色、下午紫色，卡片如何突出重点，是**表达与视觉问题**；
- A3 单幅大图、A4 地图加行程表、局部放大图如何组织，是**版式问题**；
- 输出 PDF、屏幕展示或打印，是**媒介与执行问题**。

这些决定存在约束关系，但不应被永久捆绑成一个不可拆分模板。

否则，“同一行程换一份版式”就被迫变成“重新定义一个业务场景”，领域划分是不合理的。

技术上也有可借鉴的分离方式：OGC 的 Symbology Encoding 独立定义地理数据的样式表达，SLD 则处理如何控制地理数据的视觉呈现。但这些先例支持的是“职责分离”，不意味着任意样式都与任意数据兼容。参见 [OGC Symbology Encoding](https://www.ogc.org/standards/se/)。

#### 2. 必要性取决于产品目标，而不是当前只有几个场景

| 产品目标 | 判断 |
|---|---|
| 永远只生成一种固定规格的调研图 | 完整检索与组合不是必需 |
| 同一业务需要多种视觉方案、纸张和内容组织 | 风格、版式解耦有必要 |
| 多个业务复用相同视觉语言和版式 | 通用模板接口有必要 |
| 希望 LLM 根据需求设计，而不是选择固定脚本 | 检索、组合、验证闭环有必要 |
| 希望成熟设计能够沉淀、升级、复用 | 独立模板生命周期有必要 |

**对于“制图智能体平台”，我认为有必要。**

不过，这不意味着每次制图都要重新搜索和组合。完整场景模板仍然应该保留，作为一个已经配置好的默认方案：

```text
简单需求 → 直接使用默认组合
明确改样式 → 保留业务和版式，仅替换 Style
明确改版式 → 保留业务和表达，仅替换 Layout
开放式设计 → 检索、组合、预览比较
```

这是“既支持开箱即用，也支持设计自由”，不是二选一。

---

### 二、最重要的前提：重新明确各部分的职责

我建议目标模型如下：

| 部分 | 应当拥有的内容 | 不应拥有的内容 |
|---|---|---|
| **Scenario：场景方案** | 业务任务、数据角色、必需内容、语义约束、默认组合 | 不必要地锁死颜色、字号、纸张 |
| **Expression：表达定义与本次表达选择** | 数据如何映射为视觉变量、分类或比例语义、图例语义 | 页面框坐标 |
| **Style：制图表达规范** | 兼容的符号外观、配色、线条、文字层级、卡片外观 | 具体行程数据、业务字段名、页面位置 |
| **Layout：版式** | 画布、内容容器、空间关系、容量、允许的适配行为 | 哪条路线重要、哪些地点可以删除 |
| **项目实例** | 数据绑定、标题、实际分组、选中的模板、实例参数 | 改写已发布模板 |
| **Renderer：执行后端** | 测量、绘制、合成、导出 | 临时重新选择样式或版式 |

#### 一个关键区别：修改外观，不等于修改表达含义

例如：

- 上午从蓝色改为绿色，可以是样式调整；
- 颜色从“表示上午/下午”改为“表示路线拥堵程度”，不是样式调整，而是表达方案变化；
- 卡片字体变小，是视觉调整；
- 为了放得下而删除某个调研地点，是业务内容变化。

**组合系统必须识别这些区别，不能都归入 `style_overrides`。**

同时，模板是包装和复用方式，不必与运行时对象严格一一对应：一个场景模板可以带默认 Style 和 Layout，但各部分必须保留清晰的所有权，不能重复生效。

---

### 三、“自由组合”应当怎样实现？

#### 1. 自由的是选择与设计，不是取消兼容性

合理的组合，需要同时满足四类条件：

1. **语义兼容**  
   Style 支持当前表达需要的视觉角色，不能改变数据含义。

2. **接口兼容**  
   Scenario 需要的内容，在 Layout 中有对应容器；表达需要的符号，在 Style 中有对应配置。

3. **物理兼容**  
   字号、卡片数量、地图框大小、图例容量等，在实际内容下能够成立。

4. **执行兼容**  
   后端能够实现所需的符号、字体、裁剪、叠绘和输出。

例如：

> 一个 Style 要求正文至少 12pt；某个 Layout 的侧栏只能容纳 6 张卡片；实际行程有 12 张卡片。

Style 和 Layout 各自合法，但当前组合不成立。

系统不能悄悄缩到 6pt 或删除一半内容。它应报告冲突，由设计者选择分页、换版式、改变卡片呈现方式，或者在业务允许下调整内容。

#### 2. 检索要分清“适用”与“偏好”

建议检索流程为：

```text
用户目标、业务要求、已获准的数据概要、输出约束
                    ↓
             构建设计需求
                    ↓
    检索场景方案 / Style / Layout 候选
                    ↓
        核验硬条件，标记缺失与不兼容
                    ↓
       按视觉偏好、适配程度等辅助排序
                    ↓
          LLM 提出具体组合与参数
                    ↓
          联合验证、渲染、视觉审查
                    ↓
               选择并冻结
```

这里应坚持：

- 相似度高，不代表合法；
- 检索分数，不代表最终设计决定；
- 未知条件，不能当作满足；
- 没检索到，不代表库里一定没有；
- 库中没有现成预设，不代表无法构造合法方案。

**检索器负责提供候选与证据，LLM/用户负责设计选择，程序负责形式验证。**

#### 3. 组合必须显式，不应依赖加载顺序

不建议：

```text
加载 Scenario
→ 加载 Style 覆盖一遍
→ 加载 Layout 再覆盖一遍
→ 最后让用户参数覆盖所有东西
```

建议区分三种操作：

| 操作 | 含义 |
|---|---|
| **替换组件** | 用另一份完整 Style 或 Layout 替换对应部分 |
| **实例化参数** | 在模板公开的参数接口内选择字号、行列数、间距等 |
| **派生设计** | 超出原模板接口，形成有来源记录的新设计草稿 |

硬约束需要共同满足，不能被“用户参数优先”覆盖；默认值可以调整，但必须处于明确的作用域和参数范围内。

---

### 四、最值得做的架构调整

#### 1. 将业务能力与具体模板身份解耦

目标不应是：

```text
领导调研能力 = leadership-visit-map@某固定版本
```

而应是：

```text
领导调研能力
  → 声明业务任务、输入语义、必要表达、质量要求
  → 接受满足这些条件的场景方案与组合
```

这样：

- 一个业务场景可以有多个场景模板；
- 一个 Style 可以服务多个场景；
- 一个 Layout 可以承载不同业务内容；
- 增加兼容的 Style/Layout，不需要修改业务插件。

但模板不能自行赋予系统新能力。新增一种真正没有实现的表达方法或渲染特性，仍需要相应实现与验证。

#### 2. 建立统一的内容角色、视觉角色和版式插槽

这是组合能否成立的关键，比检索算法更重要。

以领导调研为例，可以区分：

```text
业务内容角色：
  调研点、路线、辅助地点、行程说明、来源声明

表达/视觉角色：
  分类路线、编号点、辅助标记、信息卡片、说明文字

版式内容插槽：
  主地图、标题、图例、行程列表、来源区、局部视图
```

三者通过显式绑定连接：

```text
调研点
  → 编号点 + 信息卡片
  → 主地图内注记或侧栏卡片容器
```

Style 不需要知道具体地名，Layout 不需要知道“上午组”是什么。

**通用性应建立在这些接口上，而不是要求所有模板认识同一批业务字段。**

#### 3. 将真正生效的外观配置统一到同一条消费链

目标应保证：

```text
选中的 Style
  → 已解析外观
  → 图形实例
  → 所有渲染输出
```

不能出现：

- 通用 Style 写着一套字号；
- 场景私有样式又写一套；
- 渲染器还有一套兜底；
- 前端再调整一次。

对于领导调研，建议把其中可通用的能力抽出来：

- 分类路线与方向箭头；
- 编号点；
- 信息卡片；
- 引线；
- 辅助地点标签；
- 图例外观。

场景层保留“哪些内容采用哪种表达”的业务决定；通用表达组件和 Style 负责“怎样绘制”。

这不是要求删除场景插件，而是**让场景插件不再垄断通用视觉能力**。

#### 4. 让 Layout 成为真实的页面构成合同

Layout 不应只是四个固定矩形，也不应被迫全部变成复杂约束求解器。

目标可以同时支持：

- 固定版式；
- 参数化网格；
- 主图加侧栏；
- 非等分多图；
- 局部放大图；
- 明确声明空间关系的自由编排。

它们应统一解析为相同的布局实例，而不是分别建立几套绘图引擎。声明式视图组合有成熟的技术先例，例如 Vega-Lite 将叠加、分面、拼接和重复视图纳入组合语法；可以借鉴这种组织思想，但不必采用其全部实现。参见 [Vega-Lite View Composition](https://vega.github.io/vega-lite/docs/composition.html)。

需要明确：

- 哪些内容必须出现；
- 哪些内容可以重复；
- 内容与视图如何绑定；
- 是否允许包含或重叠；
- 最小可读尺寸；
- 溢出时允许换列、分页还是必须拒绝。

**真正重要的是所有声明都能被消费、验证和冻结，而不是支持尽可能多的字段。**

#### 5. 用统一编译实例连接组合与渲染

组合结果不应直接变成一堆对渲染器的临时指令，而应归一为一份完整实例：

```text
业务语义与数据绑定
＋ 本次表达选择
＋ 选中的 Style 与参数
＋ 选中的 Layout 与内容绑定
＋ 输出与后端约束
              ↓
     唯一的已解析制图实例
              ↓
       预览、检查、冻结、渲染
```

每个最终值应能回答：

- 来自哪个模板？
- 是默认值还是项目决定？
- 是否经过适配？
- 受什么约束？
- 由哪些输入推导？

建议演进现有 `MapPlan`、`resolved-*`、`RenderScene`、`MapSpecLock`，**不要另建一个并行的组合执行体系**。这一方向也与仓库的 `doc/carto-template-dsg.md` §“组合、编译与冻结”一致。

#### 6. 把“使用组合”和“发布新模板”分开

不应要求每个组合都发布成一个完整新模板。

合理的结果类型是：

```text
直接复用：引用现有模板
参数实例化：现有模板 + 本次参数
项目派生：形成项目内设计草稿
正式发布：将有复用价值的设计单独入库
```

例如：

> “调研场景 + 技术风格 + A4 侧栏版式”

可以只是本次地图的设计方案，不必先创建一个新模板 ID。

只有当它成为值得复用的稳定方案时，才发布成新的场景模板。模板发布审批与地图实例审批仍应区分。

### 五、具体需要改动哪些内容？

下面是需要覆盖的工程范围，**不表示已有模块都要重写**。所有地图实现仍应集中在 `skills/carto-agent/`。

| 工作面 | 需要达到的目标 | 主要涉及位置 |
|---|---|---|
| **能力登记** | 业务能力不再与单一模板 ID/版本绑定；按语义与能力校验组合 | `scenario_registry.py`、`policies/scenario-capabilities.yaml` |
| **模板合同** | 定义角色、插槽、公开参数、组件替换、约束和精确依赖 | `schemas/scenario.schema.json`、`style.schema.json`、`layout.schema.json` |
| **检索与需求判断** | 从“相似评分”发展为需求解析、条件核验、候选解释和组合建议 | `repository/template_matching.py`、`compiler/design_requirements.py` |
| **组合与所有权** | 明确替换、实例化、派生；拒绝冲突，记录来源 | `compiler/ownership.py`、`dependencies.py`、`creation_orchestration.py` |
| **表达和样式编译** | 通用 Style 实际控制最终外观，消除场景私有配置旁路 | `compiler/appearance.py`、`portrayal_resolver.py`、场景编译器 |
| **版式编译** | 内容绑定、实际字体测量、容量验证、声明式适配、多种布局统一解析 | `compiler/layout.py`、`grid_layout.py`、`page_bindings.py` 等 |
| **生成与修订** | 将检索、组合、候选比较接入生成流程；按依赖关系失效和重编译 | `workflow/map_generation.py`、`map_planning.py`、`revision_graph.py` |
| **领导调研场景** | 保留业务语义；拆出可复用路线、编号点、卡片等表达；默认模板改为默认组合 | `scenarios/leadership_visit/` |
| **渲染、冻结与验证** | 后端消费统一实例；冻结全部组件引用和实际参数；检查组合而非只检查单模板 | `adapters/`、锁和验证相关模块 |
| **模板生命周期** | 独立 Style/Layout 的创建、验证、派生、发布，与项目内使用衔接 | `workflow/segment_workflow.py`、`segment_validation.py`、模板仓库 |

协议变化还需要同步版本化、合法/非法样例与自动测试；已冻结产物不应被静默改写。

### 六、怎样判断目标真的实现了？

我建议用行为验收，而不是用“有几个模板接口”验收。

#### 对领导调研，至少应做到

1. **同一份行程数据，替换 Style 后，地点、访问顺序、路线事实不变。**
2. **替换 Layout 后，可以改变纸张和内容组织，但必需内容不会偷偷消失。**
3. **新增一份兼容 Style/Layout，无须修改领导调研场景代码。**
4. **缺少卡片容器、图例放不下、后端不支持时，返回具体冲突，而不是回退固定模板。**
5. **每一项最终样式和布局参数，都能追溯来源。**
6. **冻结后不再重新检索、重新选模板或偷偷换版式。**
7. **形式验证通过之后，仍有视觉审查，判断可读性和设计质量。**

其中第三条是最有辨识度的：

> **如果新增一份合法版式，仍然需要修改 `RouteCandidateCompiler` 才能使用，那么组合系统还没有真正解耦。**

---

### 最后的建议

我会把目标确定为：

> **以场景方案保留业务语义，以独立 Style 和 Layout 提供可复用设计，以表达目录和统一编译器保证组合有意义、能执行、可验证。**

其中：

- **必要的**：职责解耦、统一接口、组合验证、唯一有效配置来源、实例冻结。
- **值得具备的**：候选检索、参数化适配、多个方案预览、项目派生与复用。
- **没有必要追求的**：一个万能模板、任意模板无条件互换、每次都自动搜索、所有组合都重新发布、仅靠相似度决定设计。

**所以，这不是简单“增加模板检索功能”，而是将系统从“专用模板驱动的制图程序”，提升为“业务约束下的可组合制图系统”。这个方向在领域划分和产品能力上都合理。**
