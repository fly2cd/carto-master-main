## 一、先说结论：不是重新安装 Hermes，也不是专门做一个土地覆盖程序

这次应该做的事情可以概括成一句话：

**让已经安装的 Hermes 按 Carto Skill 的制图规则，调用它真正可用的工具，把一次制图的输入、决定、执行结果和检查结果接起来。**

三者分工如下：

| 谁 | 用日常语言理解 | 负责什么 |
|---|---|---|
| 你 | 提需求和作决定的人 | 说明用途、确认数据含义、确认预览和交付 |
| Hermes | 理解需求、安排工作的人 | 读取 Skill，找可用工具，提出方案，调用工具，遇到不清楚的地方询问 |
| Carto Skill | 制图说明书和检查清单 | 规定什么算画对了，保存工作记录，检查方案与成果，管理确认和交付 |
| MCP 等工具 | 真正干活的工具 | 读取文件、分析数据、进行空间处理、绘图或导出，具体看工具实际支持什么 |

MCP 可以简单理解为 Hermes 连接外部工具的一种方式。**有 MCP 支持，不代表已经接上能读 TIFF、能做空间处理或能绘图的工具。**这几件事要分别验证。

### 本轮不做的事情

- 不重新安装 Hermes，不升级或改写 Hermes 本体。
- 不把已经存在的 Carto Skill 再复制一份到别处。
- 不因为当前示例而新增一套“土地覆盖专用主流程”。
- 不默认在 Carto 内安装一整套 GIS 软件，先使用宿主已有能力。
- 不要求每做一种地图就先开发一个新模板。
- 不把“通用”理解为可以运行任意未经检查的代码。

### 应保留什么

制图步骤可以按需求变化，但以下要求不能随意省略：数据含义明确、工具有权限、结果能核对、预览得到确认、正式成果经过检查。换一种地图，不应该改变这些基本要求。

## 三、你的土地覆盖图，最终应该怎样完成

### 3.1 当前已知数据情况

沿用此前对该 TIFF 的只读检查结果：

| 项目 | 结果 |
|---|---|
| 尺寸 | 3062 × 2494 像元 |
| 波段和数值类型 | 单波段、8 位无符号整数 |
| 文件声明的坐标系 | NAD83 / UTM zone 11N，EPSG:26911 |
| 分辨率 | 30 × 30 米 |
| 出现的数值 | `0、1、2、3、4、6、7、8、9、10、255` |
| 文件内置颜色表 | 未读到 |
| 明确的无数据标签 | 未读到 |
| 分类名称 | 仍需要重分类对照表确认 |

11 个不同数值不等于已经确认有 11 种土地覆盖类型。尤其不能自动把 `0`、`255` 当作空白，也不能猜测某个数值就是林地或水体。

这份数据已经完成分类。本次任务是把已有类别画出来，不是让 Hermes 再做一次遥感识别或数值分级。

### 3.2 完整过程，用日常工作来描述

下面是需要开发完成后的目标流程，不是当前软件已经能够直接执行的流程。

| 顺序 | 实际发生什么 | 谁主要负责 | 你能看到什么 |
|---|---|---|---|
| 1 | 确认本次任务、输入路径和可用工具 | Hermes + Carto | 可用功能和缺少功能的清单 |
| 2 | 在已有读取权限内，使用真实工具查看 TIFF，不修改原文件 | Hermes 调用工具 | 文件概况，以及这次检查的记录 |
| 3 | 核对每个数值是什么意思，确认空白和未分类如何处理 | 你 + Hermes | 一份确认过的分类对照表 |
| 4 | 确认范围、标题、配色、图例、纸张和输出文件 | Hermes 提议，你确认 | 一份“准备怎样做”的简明方案 |
| 5 | 确认允许的处理操作；将这次确认与方案绑定 | 你 + Carto | 第一次确认记录，项目中称 G1 |
| 6 | 工具按需要准备数据；不需要裁剪或换坐标时就不做 | Hermes 调用工具 | 派生文件及处理记录，原 TIFF 保持不变 |
| 7 | 根据分类对照表给不同类码配色，并安排标题、图例等 | 绘图工具 + Carto | 一份地图预览 |
| 8 | 核对地图和图例，必要时修改；确认满意的版本 | 你 + 检查程序 | 第二次确认记录，即 G2；数据、方案和工具版本随之固定 |
| 9 | 使用已经固定的内容生成正式文件，不临时换数据或换工具 | 获准绘图工具 | 正式 PDF、PNG 等批准的文件 |
| 10 | 检查颜色、图例、位置、清晰度、来源说明和文件完整性 | Carto + 检查工具 | 成品检查结果 |
| 11 | 确认具体交付文件，完整地提交到指定本地目录 | 你 + Carto | 第三次确认记录，即 G3，以及交付文件和交付回执 |

**目录读写权限和以上三次确认不是同一件事。**未来可以把界面做得容易操作，但程序仍需核对是谁确认了哪一版内容。不能由模型替你签发确认记录。

## 四、具体实施：分成七批，每批都有可检查的结果

### 第一批：让 Hermes 说清“我现在有哪些工具”

**目的：**先确认现状，不再把安装软件作为起点。

要做的工作：

1. 在实际使用的 Hermes 会话中确认工作目录是本仓库。
2. 确认会话确实能读取当前 `carto-agent`，而不是只看到一个技能名称。
3. 查看该会话实际加载的工具，分清“文件读取”“地理数据分析”“数据处理”“地图绘制”“导出”分别由谁提供。
4. 对计划使用的工具，使用小型测试文件做一次真实检查。工具列表里有名称还不够。
5. 记录工具是否可用、是否获准使用、能接受哪种输入、能返回什么结果。
6. 如确实缺少工具，再单独提出接入建议，说明要改哪项配置、需要什么权限；经确认后才安装或启用。

**针对 TIFF 的检查问题：**

- 工具能否读取波段、分辨率、坐标系和类别值？
- 能否区分有效数据、空白和未分类？
- 它是在本机运行，还是在其他机器上运行？
- 如果在远端，它并不能仅凭一个 `D:\...` 路径读取本机文件。此时优先找本地能力；确需上传时另行确认范围和去向。
- 能读 TIFF 的工具未必能画地图，绘图能力必须另查。

**本批应交付：**一张真实的“可用功能表”，而不是预设的 GIS MCP 名单。

**通过标准：**至少完成“实际工具读取小型测试文件 → 返回真实结果”的检查；明确列出未具备的能力。不能靠 Hermes 自述“我支持 GIS”判定通过。

**本批不做：**重装 Hermes、重注册已有 Skill、自动导入其他软件全部 MCP 配置、自动上传真实数据。

### 第二批：把 Hermes 做完的结果交给 Carto，而不是只留在聊天里

**目的：**让“工具做了什么”能够进入项目记录，供下一步继续使用。

建议沿用现有 `carto` 入口，补齐下面的往返过程：

```text
Carto 给出本次工作要求
    ↓
Hermes 调用已获准的真实工具
    ↓
工具产生结果或文件
    ↓
接收程序核对结果与本次要求是否匹配
    ↓
保存工作记录，Carto 继续下一步
```

不能假定运行 Python 的 `carto` 程序能直接调用 Hermes 对话里的所有工具。因此优先支持“交给宿主执行，带着结果回来继续”的方式，不要求另外写一个 Agent 或重复搭建 MCP 连接系统。

一份工作要求至少说清：读哪个输入、允许做什么、结果放在哪里、允许使用哪些工具、完成后怎样检查。

一份完成记录至少说清：实际调用了什么工具、输入是什么、产生了什么结果、是否成功、结果文件有没有变化。

接收程序应从可信的实际调用记录和可核对的产物取得这些信息，不能把模型自己编写的“执行成功”当作证明。接入实际 Hermes 记录的方式要在实施时核实；如果当前接入方式拿不到可信记录，先完成这个缺口，再开放正式生产路径。

**对 TIFF 的应用：**读取结果应成为项目内可检查的数据说明，不要求你把聊天内容复制到配置文件里。

**通过标准：**中断后能够找到已完成结果；重复回传不会重复处理；回传另一文件或另一任务的结果会被拒绝。只得到不完整文字总结时，明确提示缺项。

### 第三批：让不同工具的结果都变成一份看得懂的数据说明

**目的：**Carto 不直接依赖某个 MCP 的返回格式，更不依赖某个业务文件名。

工具 A 可能把波段数量写作一种字段，工具 B 可能使用另一种写法。接入层负责整理差异，Carto 看到的是同一类数据说明。

说明内容根据数据类型包含：

- 数据来自哪里，哪一版，有没有使用限制。
- 是栅格、图形边界还是普通表格。
- 有哪些字段或波段，它们表示什么，单位是什么。
- 地理位置、范围、坐标系等必要信息。
- 哪些值有效，哪些值代表空白或未分类。
- 分类数据的数值与名称对照关系。
- 哪些内容已经确认，哪些仍不知道。

**对 TIFF 的应用：**文件本身可以告诉我们存在数值 `3`，但不能因此猜出它的地物名称。Hermes 应向你索取重分类对照表，并保存确认结果。

**通过标准：**不同工具返回相同含义的数据后，后续制图计划不需要改变；未知类别不会被悄悄忽略；真实数据文件不进入通用模板或普通日志。

### 第四批：按需求安排步骤，而不是新增“土地覆盖专用流程”

**目的：**一套工作方式服务多种地图。

Hermes 根据数据说明、制图要求和可用工具提出计划，Carto 检查计划是否完整、是否有权限、是否真的能执行。

例如：

| 地图需求 | 本次需要的工作安排 |
|---|---|
| 土地覆盖分类图 | 读取分类结果 → 确认类别 → 类别配色 → 安排版面 |
| 行政区指标图 | 读取表格和边界 → 对应行政区 → 核对单位 → 数值分级 → 安排版面 |
| 数量比例符号图 | 读取数量 → 确认比较尺度 → 按数量计算符号面积 → 放到地图位置 |
| 饼状或柱状符号图 | 整理分组数据 → 确认分母或比较尺度 → 绘制图形 → 放到地图位置 |

共用的是确认、记录、检查和交付，不是强迫每张图使用相同的数据处理顺序。

模板也应有两种使用方式：

- 已有合适模板：复用其中规则、风格或版面，并遵守它的硬性要求。
- 没有合适模板：先形成仅用于本次任务的完整方案，经检查后执行。有复用价值时，再通过独立流程保存为模板。

**注意：**无模板的项目级方案是拟新增能力，当前程序仍有模板要求，必须正式改造后才可使用，不能在现有程序外绕过审批出图。模板创建和一次地图生成也不能互相替代审批。

**通过标准：**更换主题或输入文件，主要修改本次方案；不能因此在主程序里增加文件名、地区名或“土地覆盖”判断。对栅格、矢量等技术差异做必要适配是允许的。

### 第五批：使用已有绘图能力，但检查它是否真的画对了

**目的：**不用 Carto 从头实现所有图形，也不把任何一个绘图工具的输出自动视为正确。

先让 Hermes 根据要求选择合适的绘图能力，再把已经确认的地图方案交给它。

**关于此前提到的“是否要提前准备可信代码”：**需要的是已经验证过的执行能力，不是为每张图预写一套业务代码。饼图、柱图、面积比例符号如果已有工具能够正确绘制，就复用工具中的实现；Hermes 主要提供数据和参数，Carto 核对它是否表达正确。工具都不支持时，才考虑补充可复用的绘图或转换代码，并先完成检查和测试。不能把模型临时写出且未经验证的程序直接放进正式出图流程。

Carto 要把“想表达什么”与“用哪个工具画”分开：

| 想表达什么 | 必须守住的要求 |
|---|---|
| 类别配色 | 同一类别使用同一映射，地图和图例一致 |
| 数量大小 | 不能把面积比例误写成半径比例 |
| 饼状组成 | 必须知道各部分相对于哪个整体 |
| 柱状比较 | 比较范围内的数值尺度应明确且一致 |
| 地图上的位置 | 不能为了好看而改变地理位置或忽略坐标差异 |

**对 TIFF 的应用：**

1. 使用已确认的类码、名称和颜色对照。
2. 只有显示或范围要求需要时才处理数据，不强制进行转换。
3. 如果需要改变显示网格，采用经过确认的类别保持方式，避免生成没有含义的新类码。
4. 图例从同一份对照关系生成，不让模型另写一套。
5. 不能把一张普通 PNG 随意贴到页面，就宣称地理位置、比例尺都正确。

不预先把所有任务绑定到 MapLibre、QGIS 或其他单一软件。使用哪个工具取决于已验证的能力；现有绘图后端仍可作为其中一种实现复用。

**通过标准：**先用已知答案的小型数据检查位置、颜色、图例和无数据显示，再看真实预览。某项功能不支持时明确提示，不用外观相似的结果冒充。

### 第六批：把“确认过的预览”可靠地变成“正式交付文件”

**目的：**防止预览一版、正式出图另一版，或出图后不知道依据是什么。

沿用现有三次确认和交付机制，但去掉其中固定的洪涝内容。

需要保存并固定：输入和派生文件、类别或数值解释、颜色与图例、范围、版面、实际工具和关键版本、来源说明、最终输出要求。

这里的“固定”可以理解为给重要内容保存一个文件指纹：之后内容变了，程序能够发现。但指纹只能证明内容未变，不能证明计算本身正确，仍需要计算和制图检查。

必须做到：

- 正式出图不临时换成另一份远程数据或另一个绘图工具。
- 工具升级、关键参数改变时，判断旧预览是否还有效；必要时重新预览和确认。
- 能保存结果快照时优先保存，避免再次查询得到不同数据。
- 对不能重现或不能独立核对的部分如实说明，不作过度保证。
- 土地覆盖成果使用实际的数据来源和用途说明，不携带洪涝演示的固定免责声明。
- 纸张、分辨率和交付文件按已批准要求决定，但文件种类仍受明确的交付清单控制。
- 需要你的确认时真正停下，不能让模型替你确认。

**通过标准：**确认后修改数据或方案会被发现；缺少确认不能交付；失败或中断可以恢复；重复交付不会混入半成品或覆盖已有成果。

### 第七批：用多种地图验收通用性，再逐项开放生产使用

**目的：**证明做成的是通用能力，而不是恰好让这份 TIFF 生成一张图。

建议至少检查：

| 案例 | 主要检查内容 |
|---|---|
| 分类栅格地图 | 类别、空白、颜色、空间位置和图例 |
| 表格加行政边界地图 | 数据对应关系、单位、分级和图例 |
| 数量比例符号地图 | 数值与符号面积的关系 |
| 饼状或柱状符号地图 | 分组、分母或比较尺度、图形和地理位置 |

每个案例都使用相同的任务接收、结果回传、方案检查、预览确认和交付机制。某类表达尚无合适工具时，应列入待补齐能力，不能标记为验收通过。

生产验收还必须包括：

- 工具不可用、超时、返回不完整结果时，能解释问题而不是编造成功。
- 不读取未经授权的位置，不泄露密钥，不把原始业务数据装进模板包。
- 不仅看命令是否成功退出，还看任务是否真的已具备继续执行的条件。
- 中断后能从项目记录恢复，而不是依赖 Hermes 记住聊天过程。
- 原有洪涝测试仍通过，新能力没有破坏原有安全规则。
- 自动测试使用小型合成数据；真实 TIFF 仅用于获准的项目验收，不复制到公开测试数据中。
- 模拟工具测试只能证明接口可用；每个实际开放的工具组合仍须通过真实调用和真实绘图验收。

**通过标准：**维护一张“哪些数据、画法、工具和输出已经验收”的清单。按清单逐项开放，而不是笼统宣称支持所有生产地图。

## 七、避免重新走回案例硬编码的检查清单

每批开发结束都问以下问题：

- 换一个 TIFF 文件名，还能不能工作？
- 换一份分类字典，是否只需要换本次输入？
- 把分类栅格换成表格加边界，是否仍复用同一套工作记录和确认机制？
- 换一个提供相同功能的 MCP，是否只需要调整工具接入，而不是重写制图主流程？
- 工具真的做过的事情，是否能在项目记录里查到？
- 没有模板时，是提出完整方案，还是又要求新增专用作者程序？
- 增加新画法时，是否复用成熟绘图能力和对应检查，而不是复制一套业务工作流？
- 工具缺失时，是否明确拒绝继续，而不是悄悄换成意思不同的图？
- 是否保留了原有安全、确认和交付边界？

允许出现的是通用的数据类型处理、绘图能力适配和不同工具的接入差异。不应出现的是按某个地区、具体文件或业务案例写死的整条流程。

## 八、实施顺序与完成标志

```text
确认本机 Hermes 和真实工具
        ↓
接通任务要求与结果回传
        ↓
统一数据说明
        ↓
按需求形成可检查的制图计划
        ↓
调用合适绘图能力并检查预览
        ↓
确认、固定、正式出图和交付
        ↓
用多种地图与真实工具验收
```

可以按四个完成标志检查进度：

| 标志 | 达到什么程度 | 还不能宣称什么 |
|---|---|---|
| A：接上了 | Hermes 读到正确 Skill，真实工具读取结果能被 Carto 接收 | 不能宣称已经能画图 |
| B：能画对 | 至少代表性输入的表达、地理位置和图例经过验证 | 不能宣称已完成正式交付闭环 |
| C：能交付 | 输入、确认、正式成果和检查记录完整，失败可恢复 | 不能宣称支持所有工具和地图类型 |
| D：可按范围生产使用 | 多案例、实际后端和安全检查通过，支持范围明确 | 不能把未验收功能自动视为生产能力 |
